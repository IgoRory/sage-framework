The SAGE Framework

A repeatable, enforced path from feature idea to production-ready code — using AI as the primary executor, with human judgment at every critical gate.

Profitability Team Status: Approved ~6–7 days to live
1

What is SAGE?

SAGE = Semi-Autonomous Guided Execution. It is a structured workflow framework that rebuilds mob programming principles for distributed teams — with AI as the primary code executor and humans as the decision-makers at critical gates.

The core problem SAGE solves: as teams adopt AI-assisted development, output quality becomes inconsistent. One developer gets great results; another gets hallucinated code. One session produces verified, tested features; another produces something that breaks in review.

SAGE makes quality an enforced structural property of the process, not a function of individual skill or prompting technique. Because the gates are implemented in code — not in instructions — an AI agent cannot skip them.

Three things SAGE replaces

Story point estimation

Replaced by SAGE Intel — empirical velocity data from every completed phase. Planning uses real delivery history, not guesses.

Manual ADO work tracking

Replaced by Linear with structured states, auto-linked commits/PRs, and machine-readable metadata blocks.

"It worked on my machine" reviews

Replaced by 12 enforced hook gates — tests must pass, code review must clear Critical findings, completion reports must exist.

The Four Layers

SAGE operates across four interconnected layers. Each layer has a distinct purpose and can evolve independently.

⚡
Layer 1
Execution Structure

Four workflow modes (Mob, Sprint, Pair, Solo) matched to team configuration and feature type. Eight build steps (S1–S8) within each phase provide a consistent, verifiable delivery path.

🔒
Layer 2
Enforcement

Twelve Python hook scripts integrated into Cursor's execution layer. Every step transition is gated. Agents cannot skip steps or declare work complete without verifiable artifacts. Gates fire at the tool call level — not the instruction level.

🧬
Layer 3
SAGE Hone

The self-improving subsystem. Every session is observed via telemetry. Every 5 cycles, AI performance is evaluated and evidence-backed improvements to AI instructions are proposed. Changes require human approval before applying — the framework improves itself, under human control.

📊
Layer 4
SAGE Intel

Delivery intelligence from every completed cycle. Records velocity, calibration confidence, and agent quality rates. Powers the intel-advisor for weekly planning, release forecasting, and scope-change analysis. No human estimation required.

S1–S8 Build Steps

Every phase in every workflow mode runs the same eight build steps. The session manifest tracks which step is current. Gates fire at each transition — you cannot proceed to the next step without completing the prior one.

S1
Dev Interview

The dev-interview agent conducts a structured interview to establish the implementation plan. Plan-only mode — no code writes permitted during this step.

Plan mode enforced
S2
Implementation Plan

The implementation-planner produces a machine-readable implementation plan artifact from the S1 interview output. Required before any subsequent step can begin.

Gate: S1 artifact required
S3
Traceability Review

The traceability-reviewer checks the implementation plan against the PRD and component spec. Blocker count must reach zero before proceeding to S4.

Gate: Zero blockers required
S4
Validation Mockup

The plan-preview-generator produces a plan preview artifact (canvas or Markdown for UI phases, calculation proof for calculation phases). A human developer must manually set validationConfirmed: true in the session manifest — an agent cannot set this flag. Build cannot start until confirmed.

Human confirmation required
S5
Build / TDD

The primary build step. Agent runs test-driven development with required reference files loaded. The optional code-simplifier runs post-RGR to clean up complexity. In Sprint mode, dependent phases are gated until foundation phases merge.

Gate: Required refs + validation confirmed
S6
Code Review

The code-reviewer performs a structured review against the implementation plan. Proceeding requires zero unresolved Critical findings.

Gate: No Critical findings
S7
Agent Testing

The test-runner executes the test suite. The gap-analyzer checks for coverage gaps using Playwright MCP (when enabled). Test results file must contain STATUS: PASS.

Gate: STATUS: PASS required
S8
Completion Report

The feature-doc-generator produces the completion report and posts to the phase issue. The stop gate fires here — S8 cannot complete without a passing test results file from S7.

Gate: Pass evidence required to stop → Telemetry recorded

Build Modes: Autonomous vs Checkpoint

At S1 (Dev Interview), the developer sets the build mode for their phase. This choice controls how much the agent batches work before pausing for human review. Both modes run the same S1–S8 gates — the difference is in pacing and visibility during S5.

AUTONOMOUS
Full-run mode

The agent executes the entire S5 build cycle without pausing for human confirmation between tasks. It works through the TDD task list end-to-end, running tests after each task and self-correcting on failures.

⚡
Speed: Fastest time to completion — no interruptions between tasks.
🎯
Context: Agent maintains full context across the entire phase build.
👁️
Visibility: Developer reviews the full output at S6 (code review) rather than during the build.
🔒
Gates still enforced: All 12 hook gates still fire. The agent cannot skip S6, S7, or S8 regardless of mode.
Use when: the phase is well-understood, the implementation plan is detailed, and you want maximum throughput with review at code review time.
CHECKPOINT
Batch-confirm mode

The TDD task list is split into confirmation batches (defined in the session manifest). The agent builds one batch, pauses, and waits for the developer to review and confirm before proceeding to the next batch.

🛑
Pause points: Agent stops after each batch and waits for a developer to set the confirmation flag in the manifest.
🔍
Visibility: Developer reviews incremental work while it is fresh, before the next batch begins.
🧭
Course-correction: Easier to catch a wrong direction early. Batch 1 output informs whether the plan needs adjusting before Batch 2 runs.
🔒
Gates still enforced: The batch_confirmation_gate hook rejects the next batch if the confirmation flag has not been set by a human.
Use when: the phase is exploratory, involves complex logic, or when you want to catch mistakes before they propagate across the full build.
How to set it: At S1, the developer records the chosen mode in the session manifest under buildMode. The orchestrator reads this value at kick-off and configures the batch confirmation blocks accordingly. Changing the mode mid-phase requires a manifest edit approved by the developer — not the agent.

Workflow Modes

Choose a mode based on team availability, feature complexity, and how much real-time collaboration adds value. All modes run the same S1–S8 steps — the difference is in team structure and kick-off format.

MOB
Mob
Single terminal, sequential phases. Full team on screen share. Driver + Navigator roles. Mob Kick-off (~2 hrs) required. Feature Walkthrough mandatory the day before.
Best for: onboarding, collaborative features, complex decisions needing collective judgment
SPRINT
Sprint
Parallel git worktrees, each developer owns one phase. Sprint Kick-off (~75 min) required. Phases run simultaneously after kick-off, then merge in dependency order.
Best for: multi-component features where parallel execution reduces delivery time
PAIR
Pair
Two developers, sequential phases, no synchronous kick-off. PRD required at Ready status. Async phase breakdown only. Good for knowledge transfer without meeting overhead.
Best for: medium complexity work where knowledge transfer adds value
SOLO
Solo
Single developer, no kick-off. No PRD required — a Linear issue is sufficient. All 12 hook gates still active. Autonomous or checkpoint build mode.
Best for: hotfixes, minor enhancements, well-scoped contained work
Phased adoption: Sprint and Solo modes launch first. Mob and Pair are introduced once Sprint is running stably. The Feature Walkthrough for Sprint is optional initially and becomes standard practice as the team builds familiarity.

Team Roles

SAGE has well-defined responsibilities for each role. The governance model assigns skill update approvals by domain — PRD-layer changes go to the PM, execution-layer changes go to the Lead Dev.

🗂️
Product Manager
PRD layer + planning
  • Authors PRDs using prd-interviewer
  • Runs prd-completeness-check (score ≥ 80 before build)
  • Facilitates Sprint and Mob kick-offs
  • Approves phase breakdowns before build begins
  • Reviews completion reports for product correctness
  • Runs intel-advisor for weekly planning cycles
  • Approves skill updates for PRD-layer skills
🛠️
Lead Developer
Framework ownership + merges
  • Owns SAGE installation and configuration on the codebase
  • Reviews and merges PRs in dependency order
  • Approves phase breakdowns alongside the PM
  • Reviews SAGE Hone performance reports
  • Acts on systematic violation flags within one work cycle
  • Maintains hook scripts and workflow-config.json
  • Approves all execution-layer skill updates
💻
Developers
S1–S8 per phase
  • Run the full S1–S8 cycle on assigned phases
  • Choose Autonomous or Checkpoint build mode at S1
  • Manually confirm validation mockup at S4 (edits session manifest)
  • Post completion reports to phase issues at S8
  • Act as Driver or Navigator in Mob mode sessions
🔍
QA (optional, pre-live)
Observer + async review
  • Attends Mob sessions as QA Observer (optional)
  • Reviews completion reports asynchronously
  • A formal QA gate will be added before the framework is used in production release cycles
  • Extension is configuration-level — no structural rebuild needed

AI Agents

SAGE ships with 15 purpose-built AI agents. Each has a defined model, access scope, and constraints. The agents are installed as .cursor/agents/*.md files in the codebase — Cursor loads them automatically when invoked.

orchestrator
Primary coordinator. Manages kick-offs, session manifests, phase transitions, and Review & Merge.
sprint-coordinator
Read-only Sprint observer. Surfaces per-lane status and merge sequencing on demand.
dev-interview
Conducts S1 structured interview. Plan-only mode — no file writes permitted.
implementation-planner
Produces the S2 machine-readable implementation plan from interview output.
traceability-reviewer
S3 — validates implementation plan against PRD. Must reach zero blockers.
plan-preview-generator
S4 — produces plan preview artifacts (canvas, Markdown, or calculation proof) for human sign-off.
code-simplifier
Optional S5 post-build simplification. Reduces complexity without changing logic.
code-reviewer
S6 — structured code review against the implementation plan. Blocks on Critical findings.
test-runner
S7 — executes the test suite. Must produce STATUS: PASS file to proceed.
gap-analyzer
S7 — optional Playwright MCP testing to identify coverage gaps.
feature-doc-generator
S8 — produces completion report and posts to the phase issue.
session-performance-evaluator
SAGE Hone — evaluates every session, flags violations, posts Notion report.
skill-effectiveness-evaluator
SAGE Hone — every 5 cycles, proposes evidence-backed skill updates for approval.
intel-recorder
SAGE Intel — records velocity, calibration, and agent quality data after each cycle.
intel-advisor
SAGE Intel — answers planning questions using the empirical dataset. No estimation.

What counts as "ready to go live"

The first live session (Phase 7) should use a feature that is real but low-risk — not on the critical delivery path — multi-component (suited to Sprint mode), and well-understood by the team. This session doubles as a framework validation run and produces the first SAGE Intel data point.

Operating Principles

These five principles govern how SAGE is designed and how it should be operated. When something doesn't seem to fit, these are the rules to reason from.

01
Structural enforcement over agent instruction

Quality gates are hook scripts that reject tool calls at the execution layer. They do not rely on agent compliance with instructions. An AI agent cannot skip a step or declare work complete without verifiable evidence — regardless of what it is instructed to do.

02
Artifact quality determines pipeline quality

The highest-leverage quality investment is at PRD creation and phase breakdown — before any code is written. A feature cannot enter the build phase without a PRD scoring 80/100 or above. The component specification is a required artifact, not a best-effort addition.

03
Async-first, synchronous by exception

Synchronous sessions (kick-offs, feature walkthroughs) are reserved for decisions that genuinely benefit from real-time discussion. Everything else flows asynchronously so that no team member's execution is blocked by another's schedule or time zone.

04
Evidence over estimation

No human estimation is used at any stage of planning. All effort estimates and release forecasts are derived from the SAGE Intel empirical dataset, which grows with every completed work cycle. The first 5–9 completed phases per layer type build the initial calibration baseline.

05
Self-improvement is automatic, approval is human

SAGE Hone proposes improvements to AI instructions based on evidence from real sessions. Every proposed change is staged for human review before being applied. The framework improves from the bottom up — no manual tuning required. The PM approves PRD-layer changes; the Lead Dev approves all execution-layer changes.
