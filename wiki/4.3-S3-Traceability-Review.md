# S3 — Traceability Review

The [traceability-reviewer](1.3-Glossary) agent performs a bidirectional verification between the PRD requirements and the implementation plan. It is strictly read-only — it does not modify the PRD, the implementation plan, or any other file. It reports what it finds.

---

## Bidirectional trace

The review checks two directions:

### Forward trace: PRD → Implementation Plan

Every PRD requirement that falls within the current [phase](1.3-Glossary) scope must map to at least one item in the implementation plan. A requirement with no corresponding implementation item is a gap.

### Backward trace: Implementation Plan → PRD

Every item in the implementation plan must trace back to at least one PRD requirement. An implementation item with no PRD justification is scope creep or an undocumented assumption.

> **🤖 AGENT ACTION** — The traceability-reviewer reads the PRD (from Notion via MCP), the implementation plan, and the TDD spec. It performs both forward and backward traces, classifies each finding, and writes the review document to the phase directory.

---

## Finding severities

| Severity | Criteria | Examples |
|---|---|---|
| **Blocker** | A requirement has no implementation coverage, or an implementation item directly contradicts a requirement | PRD requires a rollback confirmation dialog; plan has no dialog component. Plan adds a bulk-delete endpoint; PRD does not mention bulk operations. |
| **Major** | Ambiguous mapping between requirement and implementation, or scope extension without explicit requirement justification | Plan maps "handle errors" to a generic toast; PRD specifies per-field inline validation. Plan adds an export feature "for completeness" with no PRD mention. |
| **Minor** | Naming inconsistencies, structural suggestions, non-functional gaps | Plan uses `costCentre` where PRD uses `cost_center`. Test file structure does not match the project convention. |

---

## The Blocker findings line

The traceability review document must contain the following exact line:

```
Blocker findings: N
```

Where `N` is the integer count of Blocker-severity findings. This format is machine-read by the [manifest-step-gate](6.2-Enforcement-Reference) — the gate parses this exact substring to determine whether S4 can proceed.

> **🔒 ENFORCEMENT POINT** — `manifest-step-gate` blocks S4 from starting unless the traceability review exists AND contains `Blocker findings: 0`. If any Blocker findings are present, the pipeline halts. The implementation plan must be revised (returning to S2) to resolve the Blockers before S3 is re-run.

---

## What happens when Blockers are found

When the traceability-reviewer reports Blocker findings:

1. The gate blocks S4 entry
2. The developer reviews the Blocker descriptions in the traceability review
3. The implementation-planner is re-invoked at S2 to address the gaps
4. The traceability-reviewer re-runs at S3
5. The cycle repeats until `Blocker findings: 0`

Major and Minor findings do not block progression. They are recorded for the developer's awareness and may be addressed during S5 build.

---

## Enforcement

> **🔒 ENFORCEMENT POINT** — `manifest-step-gate` blocks S3 from starting unless `phase-{N}-implementation-plan.md` exists in the phase directory.

The traceability-reviewer is strictly read-only. It never modifies the PRD, implementation plan, TDD spec, or any other file.
