# Linear Configuration

SAGE uses [Linear](1.3-Glossary) for issue tracking across four issue types: feature issues, phase issues, skill-update issues, and violation issues. Each type follows a defined state machine. State transitions drive [gate](6.2-Enforcement-Reference) behaviour — the [phase-approval-gate](6.2-Enforcement-Reference) reads Linear status to determine whether build work can begin.

---

## Feature issue states

Feature issues track an entire feature from initial idea through to delivery.

```
Backlog → PRD In Progress → PRD Under Review → Ready → Planned
```

| State | Meaning | Transition trigger |
|---|---|---|
| Backlog | Feature identified, not yet started | Manual |
| PRD In Progress | [prd-interviewer](6.4-Skill-Catalogue) is actively conducting the interview | Automatic on interview start |
| PRD Under Review | PRD draft complete, awaiting [completeness check](3.1-PRD-Creation) | Automatic on draft generation |
| Ready | PRD passed completeness threshold (≥80/100) | Set by [prd-completeness-check](6.4-Skill-Catalogue) |
| Planned | Feature assigned to a work cycle | Manual (planning cycle) |

---

## Phase issue states

Phase issues track individual phases within a feature. State machines vary by [workflow mode](1.3-Glossary).

### Sprint mode

```
Pending Approval → Approved → Foundation Verified → In Progress → Build Complete → Done
```

The `Foundation Verified` state exists only in Sprint mode. It is set by the [orchestrator](6.3-Agent-Catalogue) after Foundation and Independent phases merge and post-merge regression passes. [Dependent](1.3-Glossary) phases cannot enter S5 until this state is reached.

### Mob, Pair, and Solo modes

```
Pending Approval → Approved → In Progress → Build Complete → Done
```

No `Foundation Verified` state — phases execute sequentially, so foundation verification is implicit.

> 🔒 **ENFORCEMENT POINT** — The [phase-approval-gate](6.2-Enforcement-Reference) blocks S1 from starting until the phase Linear issue status is `Approved` or a downstream status.

## Skill-update issue states

Skill-update issues track proposed improvements to SKILL.md files from the [SAGE Hone](5.2-SAGE-Hone-Skill-Improvement) pipeline.

```
Pending Approval → Approved → Applied
                 ↘ Rejected—recorded
                              Approved → Apply Failed
```

| State | Meaning |
|---|---|
| Pending Approval | Evaluator has staged a diff and created the issue |
| Approved | Human approver has reviewed and approved the change |
| Applied | Diff applied to SKILL.md, committed to repository |
| Rejected—recorded | Change rejected, recorded in `skill-update-history.jsonl`, suppressed for 2 cycles |
| Apply Failed | Automatic application failed (merge conflict, validation error) |

> 🔵 **HUMAN ACTION** — The approver (PM or Lead Dev, per the [approval routing table](5.2-SAGE-Hone-Skill-Improvement)) reviews the staged diff and moves the issue to `Approved` or `Rejected—recorded`.

---

## Violation issue states

Violation issues track systematic [gate](1.3-Glossary) violations detected by the [session-performance-evaluator](5.1-SAGE-Hone-Session-Performance).

```
Needs Review → Closed
```

> 🔵 **HUMAN ACTION** — The Lead Dev reviews the violation, determines root cause, and closes the issue with a resolution note.

## Labels

| Label | Purpose | Applied by |
|---|---|---|
| `skill-update` | Marks skill improvement proposals | [skill-effectiveness-evaluator](6.3-Agent-Catalogue), [prd-interviewer-effectiveness-evaluator](6.3-Agent-Catalogue) |
| `violation` | Marks systematic gate violations | [session-performance-evaluator](6.3-Agent-Catalogue) |

### SAGE Workflow Mode label group

| Label | Applied when |
|---|---|
| `mode:mob` | Feature uses Mob workflow mode |
| `mode:sprint` | Feature uses Sprint workflow mode |
| `mode:pair` | Feature uses Pair workflow mode |
| `mode:solo` | Feature uses Solo workflow mode |

Mode labels are applied to feature issues and phase issues by the [phase-splitter](6.4-Skill-Catalogue) at kick-off.

## SAGE metadata block

Skill-update and phase issues include a YAML metadata block in the issue description. This block is read by agents and hooks to locate worktrees, staged diffs, and track evaluation cycles.

```yaml
---
sage_metadata:
  worktree_path: C:\Sage\worktrees\LIN-4821\phase-1\
  diff_path: .sage/skill-update-staging/LIN-512-diff.md
  evaluation_cycle: 3
---
```

| Field | Written by | Applies to | Read by |
|---|---|---|---|
| `worktree_path` | [phase-splitter](6.4-Skill-Catalogue) | Phase issues (Sprint/Pair only) | [orchestrator](6.3-Agent-Catalogue), [sprint-coordinator](6.3-Agent-Catalogue) |
| `diff_path` | [skill-effectiveness-evaluator](6.3-Agent-Catalogue) | Skill-update issues only | Evaluator apply step |
| `evaluation_cycle` | [skill-effectiveness-evaluator](6.3-Agent-Catalogue) | Skill-update issues only | Evaluator (suppression tracking) |

## Linear ↔ GitHub integration

When operational, this integration provides:
- Auto-link commits to Linear issues via `LIN-[id]` in commit messages
- Auto-link pull requests to issues
- Automatic status updates when PRs merge

> ⚠️ **KNOWN GAP — Linear ↔ GitHub integration blocked.**
> This integration requires Linear Workspace Admin access. The PM and Lead Dev are awaiting this access (implementation tracker Phase 3, step 3.6). Without it, commit and PR auto-linking do not work. Developers must manually reference Linear issue IDs in commit messages and manually update Linear status after PR merges.
