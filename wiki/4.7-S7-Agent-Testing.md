# S7 — Agent Testing

S7 is a fully automated step. No human input is required or expected during execution. Two agents work together: the [test-runner](1.3-Glossary) executes the full test suite and the [gap-analyzer](1.3-Glossary) generates additional scenarios that were not in the original TDD spec.

---

## Entry gate

> **🔒 ENFORCEMENT POINT** — `code-review-gate` blocks S7 from starting unless `phase-{N}-code-review.md` exists in the phase directory AND contains the exact substring `Critical findings: 0`. All Critical findings from S6 must be resolved before agent testing begins.

---

## Execution sequence

> **🤖 AGENT ACTION** — The test-runner and gap-analyzer execute in the following sequence:

| Order | Action | Agent |
|---|---|---|
| 1 | Run the full TDD test suite for the phase | test-runner |
| 2 | Confirm all tests pass across all phase [scoped files](1.3-Glossary) | test-runner |
| 3 | Signal the gap-analyzer to begin | test-runner |
| 4 | Generate additional test scenarios not in the TDD spec | gap-analyzer |
| 5 | Execute automatable gap scenarios | test-runner |
| 6 | Compile all results into a single document | test-runner |
| 7 | Write `phase-{N}-test-results.md` | test-runner |

---

## Gap analysis

The gap-analyzer agent generates additional test scenarios that go beyond the TDD spec. These cover areas that structured TDD specifications tend to miss:

- **Integration paths** — interactions between components that were tested in isolation during S5
- **UI state transitions** — sequences of user actions that move components through multiple states
- **Data volume edge cases** — behaviour with large datasets, empty datasets, single-record datasets
- **Permission boundaries** — actions attempted by users without the required permissions
- **Business logic edge cases** — boundary values in financial calculations, rounding at extreme ranges, allocation to zero-balance accounts

The gap-analyzer appends its findings and test results to the test results document. It never overwrites existing results from the TDD suite.

> **🤖 AGENT ACTION** — The gap-analyzer reads the implementation plan, PRD, component specification, and the code written during S5. It identifies scenarios not covered by the TDD spec, generates tests for those scenarios, and passes them to the test-runner for execution.

---

## Playwright E2E testing

End-to-end testing via Playwright is controlled by a feature flag in `workflow-config.json`:

```json
"featureFlags": {
  "playwrightE2E": true
}
```

When `playwrightE2E` is `true` (current setting), the test-runner includes Playwright-based end-to-end tests in the S7 suite. These tests exercise the full application stack — UI interactions, API calls, database operations — in a browser environment.

---

## Test results format

The test results file `phase-{N}-test-results.md` must contain one of these lines on its own (not inline with other text):

```
STATUS: PASS
```

or

```
STATUS: FAIL
```

This format is machine-read by the `completion-report-stop-gate` at S8.

---

## ADO handoff

The `sage-s7-ado-handoff` agent serves as a mapping reference between SAGE S7 testing and Azure DevOps test plans. SAGE S7 and ADO test plans are complementary — neither replaces the other.

- SAGE S7 runs automated agent testing within the build pipeline
- ADO test plans capture human QA testing managed separately
- After S7 produces `STATUS: PASS`, ADO updates follow as part of the downstream process

---

## Enforcement

> **🔒 ENFORCEMENT POINT** — `code-review-gate` blocks S7 entry unless `Critical findings: 0` is present in the code review document. This is an exact substring match — no variations are accepted.

> **🔒 ENFORCEMENT POINT** — `completion-report-stop-gate` at S8 requires `phase-{N}-test-results.md` to exist with `STATUS: PASS`. If S7 writes `STATUS: FAIL`, S8 cannot complete. See [S8 — Completion Report](4.8-S8-Completion-Report) for details on the stop-gate.
