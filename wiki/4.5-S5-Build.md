# S5 — Build

S5 is the most enforcement-dense step in the sequence. It is where code is actually written. Three gates must pass before any code writing begins, a background agent simplifies code after every completed task, and (in Checkpoint mode) the developer approves each batch before the next one starts.

---

## Entry gates

All three gates must pass before ANY code-writing tool call is permitted. The gates fire on `preToolUse` — every attempt to write code is checked.

### Gate 1: validation-confirmed-gate

> **🔒 ENFORCEMENT POINT** — `validation-confirmed-gate` blocks all S5 build tool calls until `phases[N].runtime.validationConfirmed === true` in the [session manifest](1.3-Glossary). The developer must have reviewed the S4 validation artifact and set this flag manually. See [S4 — Plan Validation](4.4-S4-Plan-Validation).

### Gate 2: required-references-gate

> **🔒 ENFORCEMENT POINT** — `required-references-gate` blocks S5 build tool calls until every file listed in `phases[N].definition.requiredReferences` has been read in the current session. The gate checks [telemetry](1.3-Glossary) for `read_file` events matching each required reference path. This ensures the build agent has seen the context it needs before writing code.

If the gate blocks, the agent must read the missing files before attempting to write code again. The telemetry logger records every `read_file` call, and the gate re-evaluates on the next tool call.

### Gate 3: foundation-verified-gate (Dependent phases only)

> **🔒 ENFORCEMENT POINT** — `foundation-verified-gate` blocks [Dependent phase](1.3-Glossary) lanes from entering S5 until `sessionState.foundationVerified === true` in the session manifest. This flag is set by the [orchestrator](6.3-Agent-Catalogue) after ALL [Foundation](1.3-Glossary) and [Independent](1.3-Glossary) phases have merged to main and the post-merge regression suite passes.

**This gate does not apply to Foundation or Independent phases.** Foundation phases (Tier 0, with downstream consumers) and Independent phases (Tier 0, no downstream consumers) proceed directly to S5 after S4 confirmation. Only Dependent phases (Tier 1+, with upstream dependencies) are blocked.

## Autonomous build mode

In [Autonomous mode](1.3-Glossary), the build agent completes all tasks end-to-end without pausing for developer review.

### Red-Green-Refactor cycle

The [test-runner](1.3-Glossary) agent executes the [Red-Green-Refactor](1.3-Glossary) TDD cycle for each task in the implementation plan:

1. **RED** — Write a failing test that expresses the expected behaviour
2. **GREEN** — Write the minimum production code to make the test pass
3. **REFACTOR** — Clean up the code while keeping all tests green

> **🤖 AGENT ACTION** — The test-runner processes tasks in the dependency order defined in the implementation plan. For each task: write the failing test, confirm it fails, write the production code, confirm the test passes, refactor if needed, confirm tests still pass.

### Code simplification

After each completed task, the [code-simplifier](1.3-Glossary) agent runs automatically as a background process.

> **🤖 AGENT ACTION** — The code-simplifier applies simplification changes directly to the code written in the completed task. It looks for:
> - **Code duplication** that can be extracted into shared functions
> - **Unnecessary complexity** — nested conditions, over-engineered patterns
> - **Naming** that does not reflect purpose
> - **Dead code** that serves no function
>
> After each simplification change, the code-simplifier runs the test suite. If any test fails, the change is reverted immediately. The simplifier never adds functionality — it only simplifies.

The code-simplifier has two hard constraints:
- **Never touches test files** — tests are the specification, not the target of simplification
- **Never reorders stored procedure calculation sequences or financial logic** — FTP calculations, allocation logic, and similar sequential operations are left in their authored order

### TDD results

After all tasks complete, the test-runner writes `phase-{N}-tdd-results.md` to the phase directory. This file must contain `STATUS: PASS` on its own line when all tests are green.

> [**DIAGRAM PLACEHOLDER — Autonomous Build Flow**]
>
> Vertical flow starting at "Entry Gates Pass". Each task is a repeating loop: RED (write failing test) → GREEN (write passing code) → REFACTOR (clean up). After each task loop, a "code-simplifier" box runs with a conditional branch: "Tests pass → keep changes" or "Tests fail → revert." After all tasks complete, a final box writes "phase-{N}-tdd-results.md with STATUS: PASS". Arrows flow strictly downward. Label the entry point with the three gate names.

## Checkpoint build mode

In [Checkpoint mode](1.3-Glossary), the same Red-Green-Refactor cycle runs, but tasks are grouped into 2–4 [batches](1.3-Glossary). After each batch, the agent pauses for developer review.

### Batch execution

Batches follow the boundaries defined at S2 (see [S2 — Implementation Plan](4.2-S2-Implementation-Plan) for the `batchBoundaryRules` table). The agent processes all tasks within a batch using the same RGR cycle, then:

1. Runs all tests for the batch
2. Writes a batch review document: `phase-{N}-batch-{M}-review.md`
3. Pauses and waits for developer confirmation

The batch review document contains:
- Files changed in this batch
- Methods and classes added or modified
- Batch test results (pass/fail per test)
- Any deviations from the implementation plan

> **🔵 HUMAN ACTION** — Review the batch output. Read `phase-{N}-batch-{M}-review.md`. Inspect the code changes. When satisfied, confirm the batch by editing the session manifest:
>
> 1. Open `.sage/sessions/[session-id]/session-manifest.md`
> 2. Find `phases[N].runtime.batches[currentBatchId].confirmed`
> 3. Change `false` to `true`
> 4. Save the file

> **🔒 ENFORCEMENT POINT** — `batch-confirmation-gate` blocks the next batch's build tool calls until the developer sets `batches[currentBatchId].confirmed=true` in the session manifest. Like `validationConfirmed`, no agent can set this flag.

After the developer confirms, the agent proceeds to the next batch. The code-simplifier runs after each task within each batch, following the same rules as Autonomous mode.

After ALL batches complete and are confirmed, the test-runner writes the full `phase-{N}-tdd-results.md` with `STATUS: PASS`.

> [**DIAGRAM PLACEHOLDER — Checkpoint Build Flow with Batch Boundaries**]
>
> Vertical flow with horizontal dividers separating batches. Each batch contains the same RGR task loops as Autonomous mode. After each batch section, a "Batch Review" box connects to a "🔵 Developer Review" decision point, which connects to a "batch-confirmation-gate" bar. The gate has two paths: "confirmed=true → proceed to next batch" and "confirmed=false → BLOCKED." After all batches, the flow reaches "phase-{N}-tdd-results.md with STATUS: PASS." Label each batch with its boundary rule name (e.g., "Batch 1: schema-and-migrations").

## Foundation and Dependent phase timing

How phases interact during S5 depends on their [phase type](1.3-Glossary):

| Phase type | S1–S4 | S5 Build | Merge |
|---|---|---|---|
| **[Foundation](1.3-Glossary)** (Tier 0, has downstream consumers) | Starts immediately | Starts immediately after S4 | Merges first |
| **[Independent](1.3-Glossary)** (Tier 0, no downstream consumers) | Starts immediately | Starts immediately after S4 | Merges alongside Foundation |
| **[Dependent](1.3-Glossary)** (Tier 1+, has upstream dependencies) | Starts immediately — can complete S1–S4 in parallel | **Blocked** until `foundationVerified=true` | Merges after Foundation and Independent |

Dependent phases are not idle during the Foundation build. They complete S1 through S4 (Developer Interview, Implementation Plan, Traceability Review, Plan Validation) while Foundation phases are building. The only step they cannot enter is S5.

> **🤖 AGENT ACTION** — The orchestrator sets `sessionState.foundationVerified=true` after ALL Foundation and Independent phases have merged to main and the post-merge regression suite passes. This unlocks the `foundation-verified-gate` for all Dependent phases simultaneously.

The Foundation lane shows S1→S2→S3→S4→S5→S6→S7→S8→Merge→Regression as a continuous flow. ## What S5 produces

| Artifact | Contents |
|---|---|
| Source files | All production code and test files created or modified during the build |
| `phase-{N}-tdd-results.md` | Complete test results with `STATUS: PASS` on its own line (or `STATUS: FAIL` if tests do not pass) |
| `phase-{N}-batch-{M}-review.md` (Checkpoint only) | Per-batch summary of changes, test results, and deviations |

---

## Enforcement summary

S5 has more gates than any other step:

| Gate | When it fires | What it checks | Who resolves it |
|---|---|---|---|
| `validation-confirmed-gate` | Every S5 build tool call | `validationConfirmed === true` | Developer (edit manifest) |
| `required-references-gate` | Every S5 build tool call | All `requiredReferences` read in session | Agent (read missing files) |
| `foundation-verified-gate` | Every S5 build tool call (Dependent only) | `foundationVerified === true` | Orchestrator (after merge + regression) |
| `batch-confirmation-gate` | Next batch's first tool call (Checkpoint only) | `batches[N].confirmed === true` | Developer (edit manifest) |
