*This page provides a compact overview of the eight build steps (S1–S8) that every [phase](1.3-Glossary) progresses through, the agents that run each step, the artifacts produced, and the gates that enforce boundaries. It serves developers as a map before diving into individual step pages.*

---

# The Eight Build Steps — Overview

Every phase in a [session](1.3-Glossary) follows the same eight-step sequence. No step can be skipped. Each step produces a named [artifact](1.3-Glossary), and a [gate](1.3-Glossary) at each boundary checks a real-world condition before allowing progression. Three of the eight steps require explicit human action — the rest are fully agent-driven.

| Step | Name | Agent | Artifact Produced | Gate at Boundary | Human Action Required |
|---|---|---|---|---|---|
| S1 | Developer Interview | [dev-interview](6.3-Agent-Catalogue) | `phase-{N}-dev-interview-summary.md` | `plan-mode-enforcer` (blocks writes) | [Build mode](1.3-Glossary) selection |
| S2 | Implementation Plan | [implementation-planner](6.3-Agent-Catalogue) | `phase-{N}-implementation-plan.md` | `manifest-step-gate` (requires S1 artifact) | None |
| S3 | Traceability Review | [traceability-reviewer](6.3-Agent-Catalogue) | `phase-{N}-traceability-review.md` | `manifest-step-gate` (requires S2 artifact) | None |
| S4 | Plan Validation | [plan-preview-generator](6.3-Agent-Catalogue) | `phase-{N}-plan-preview.canvas.tsx` / `phase-{N}-plan-preview.md` | `manifest-step-gate` (requires S3 artifact + zero Blockers) | Confirm validation (set `validationConfirmed=true`) |
| S5 | Build | [test-runner](6.3-Agent-Catalogue) + [code-simplifier](6.3-Agent-Catalogue) | source files + `phase-{N}-tdd-results.md` | `validation-confirmed-gate`, `required-references-gate`, `foundation-verified-gate` (Dependent), `batch-confirmation-gate` (Checkpoint) | Checkpoint batch confirmations |
| S6 | Code Review | [code-reviewer](6.3-Agent-Catalogue) | `phase-{N}-code-review.md` | `tdd-results-gate` (requires `STATUS: PASS`) | None |
| S7 | Agent Testing | [test-runner](6.3-Agent-Catalogue) + [gap-analyzer](6.3-Agent-Catalogue) | `phase-{N}-test-results.md` | `code-review-gate` (requires `Critical findings: 0`) | None |
| S8 | Completion Report | orchestrator | `phase-{N}-completion-report.md` | `completion-report-stop-gate` (requires `STATUS: PASS` in test-results) | None |

## How gates work

Gates are enforced by [hook scripts](1.3-Glossary) — Python scripts registered in `hooks.json` that intercept Cursor tool calls. A gate reads a specific condition (a file exists, a flag is set, a string is present in an artifact) and either permits or blocks the tool call. No agent can instruct its way past a gate. The condition must be satisfied in the real world.

The three human-action points in the sequence are:

1. **S1** — Developer selects [Autonomous or Checkpoint](1.3-Glossary) build mode
2. **S4** — Developer reviews the validation mockup and sets `validationConfirmed=true` in the [session manifest](1.3-Glossary)
3. **S5 (Checkpoint only)** — Developer confirms each batch after reviewing its output

## Step progression rules

The [manifest-step-gate](6.2-Enforcement-Reference) enforces the general rule: before any step can begin, the prior step's artifact must exist in the phase directory. Additional gates apply at specific boundaries:

- **S1 entry** — `phase-approval-gate` checks that the phase's Linear issue status is "Approved"
- **S4 → S5** — Three gates must pass simultaneously: `validation-confirmed-gate`, `required-references-gate`, and (for [Dependent phases](1.3-Glossary) only) `foundation-verified-gate`
- **S5 → S6** — `tdd-results-gate` checks the TDD results file for `STATUS: PASS`
- **S6 → S7** — `code-review-gate` checks the code review file for `Critical findings: 0`
- **S8 exit** — `completion-report-stop-gate` fires on the `stop` event, preventing the agent from ending its turn without test evidence

---

## Artifact locations

All phase artifacts are written to `.sage/sessions/[session-id]/phase-[N]/`. The [session manifest](6.1-Session-Manifest-Reference) tracks which session is active via `.sage/sessions/active-session.txt`.
