# 3.2 Sprint Kick-off

*This page covers both the Mob kick-off (120 minutes) and the Sprint kick-off (75 minutes), explaining how each transforms a Ready PRD into an approved session with phase issues, manifests, and worktrees — and serves the Product Manager, Lead Dev, and Developers.*

| Mode | Duration | Prerequisite | Key Distinction |
|------|----------|-------------|-----------------|
| Mob | 120 min | PRD exists (prd-interviewer runs live during kick-off) | Everyone participates in the same terminal/screenshare for the PRD interview |
| Sprint | 75 min | PRD already passed prd-completeness-check (≥ 80/100) | PRD pre-reviewed; kick-off processes developer feedback from a Teams recording |

---

## Feature Walkthrough

The Feature Walkthrough is a preparatory session where the Product team member walks the team through PRD details to orient everyone before the kick-off.

> 🔵 **HUMAN ACTION**  
> The Product team member conducts the walkthrough. In-person or remote call. No agent involvement.

| Mode | Required? | Timing | Duration |
|------|-----------|--------|----------|
| Mob | **Required** | Day before kick-off | 60 min |
| Sprint | Optional | Before kick-off (no fixed timing) | As needed |

The walkthrough covers PRD content, acceptance criteria, and any domain context the team needs. For Mob mode, this ensures participants are prepared to provide input during the live [prd-interviewer](1.3-Glossary) session the following day.

---

## Mob Kick-off (120 minutes)

The Mob kick-off runs the PRD interview live with everyone present. The team provides answers collectively in a single terminal or screenshare session.

### Timeline

| Step | Duration | Activity |
|------|----------|----------|
| PRD Discussion | 45 min | Live prd-interviewer session — everyone participates |
| Phase Breakdown | 45 min | phase-splitter generates and facilitates phase review |
| Session Setup | 30 min | Manifest generation, Linear issues created |

### Step 1 — PRD Discussion (45 min)

> 🤖 **AGENT ACTION**  
> The [prd-interviewer](1.3-Glossary) skill runs in real time. The same codebase reconnaissance, complexity classification, and section-by-section interview process described in [PRD Creation](3.1-PRD-Creation) applies — but the entire team participates in answering.

This is the defining characteristic of Mob mode: everyone sees the same terminal, everyone contributes answers. The PM drives but developers provide technical input directly during the interview.

The interview produces:
- PRD at `.sage/prds/[FEATURE_ID]/prd.md` + Component Specification at `.sage/prds/[FEATURE_ID]/component-spec.md`
- `[FEATURE_ID]-interview-answers.json` at `.sage/prds/[FEATURE_ID]/`
- [prd-completeness-check](1.3-Glossary) runs at the end — score must reach ≥ 80/100 before proceeding to Phase Breakdown

### Step 2 — Phase Breakdown (45 min)

> 🤖 **AGENT ACTION**  
> The [phase-splitter](1.3-Glossary) skill runs against the completed PRD. See [Phase Breakdown Process](#phase-breakdown-process) below.

### Step 3 — Session Setup (30 min)

> 🤖 **AGENT ACTION**  
> Manifest generation, Linear phase issue creation, active-session.txt written. Mob mode does **not** create git worktrees (`worktrees: false` in workflow-config.json).

## Sprint Kick-off (75 minutes)

The Sprint kick-off assumes the PRD has already been completed and passed prd-completeness-check. Each team member has reviewed the PRD before the call.

### Timeline

| Step | Duration | Skill |
|------|----------|-------|
| Dev Review | 35 min | kickoff-dev-review |
| Phase Breakdown | 30 min | phase-splitter |
| Manifest Generation | 10 min | phase-splitter (finalisation) |

> [**DIAGRAM PLACEHOLDER — Sprint Kick-off Timeline**]

### Step 1 — Dev Review (35 min)

The team discusses the PRD on a Microsoft Teams call (~20 min). When the discussion ends, the recording is stopped but the team stays on the call.

> 🔵 **HUMAN ACTION**  
> Developers discuss the PRD on Teams. Recording stops after ~20 minutes. Team remains on call.

> 🤖 **AGENT ACTION**  
> The [kickoff-dev-review](1.3-Glossary) skill is invoked with the Teams meeting link. It fetches the transcript via Microsoft 365 MCP.

**kickoff-dev-review processes the transcript in this sequence:**

1. Fetch transcript via M365 MCP (~1 min)
2. Read PRD and Component Specification from `.sage/prds/[FEATURE_ID]/`
3. Extract every developer concern from the transcript
4. Categorise each concern into one of seven types:

| Category | Action |
|----------|--------|
| PRD_UPDATE | Draft update, confirm with team, apply to PRD file |
| PHASE_IMPLICATION | Note in phase-splitter briefing |
| CODEBASE_CONFLICT | Surface immediately, resolve with team |
| CLARIFICATION_NEEDED | Ask targeted follow-up question |
| ADDRESSED_IN_PRD | Point developer to relevant section |
| OUT_OF_SCOPE | Confirm with team, log |
| NO_ACTION | Log only |

5. Ask follow-up questions for CLARIFICATION_NEEDED and CODEBASE_CONFLICT items (~10 min with team still on call)
6. Apply confirmed PRD updates to `.sage/prds/[FEATURE_ID]/prd.md` (one at a time, each confirmed with team)
7. Re-run prd-completeness-check silently against updated PRD

> 🔒 **ENFORCEMENT POINT**  
> If prd-completeness-check drops below 80/100 after updates, the skill surfaces the new gap immediately. Hand-off to phase-splitter is blocked until score recovers.

**Outputs:**
- `[SESSION_ROOT]/kickoff-dev-review-log.md` — all concerns with categories, resolutions, and follow-up outcomes
- `[SESSION_ROOT]/phase-splitter-briefing.md` — phase implications, codebase conflicts resolved, PRD updates applied, updated completeness score

### Step 2 — Phase Breakdown (30 min)

> 🤖 **AGENT ACTION**  
> The [phase-splitter](1.3-Glossary) skill runs against the PRD + briefing note. See [Phase Breakdown Process](#phase-breakdown-process) below.

### Step 3 — Manifest Generation (10 min)

> 🤖 **AGENT ACTION**  
> On team confirmation, phase-splitter writes the session manifest, creates Linear issues, creates worktrees, and writes active-session.txt.

## Phase Breakdown Process

This process is identical for both Mob and Sprint modes. The [phase-splitter](1.3-Glossary) skill executes it.

### Inputs

| Input | Source |
|-------|--------|
| PRD | `.sage/prds/[FEATURE_ID]/prd.md` (must be at Linear status Ready) |
| Component Specification | `.sage/prds/[FEATURE_ID]/component-spec.md` |
| Phase-splitter briefing | `[SESSION_ROOT]/phase-splitter-briefing.md` (Sprint/Mob) |
| Session manifest template | `.cursor/templates/session-manifest-template.md` |
| Codebase | Read access via Cursor file system |
| Splitting heuristics | `references/splitting-heuristics.md` |

### Phase Generation Steps

1. **Codebase reconnaissance** — identify all files the feature will touch, categorised as UI / Backend-API / Data-schema / Test
2. **Generate candidate phases** — apply splitting heuristics. Each phase must have a single objective, exclusive file ownership, at least one independent test, and 2–8 hours estimated effort
3. **Score independence** — each phase scored 0–100. Phases below 60 are flagged
4. **Assign phase types:**

| Type | Condition | Behaviour |
|------|-----------|-----------|
| Foundation | No upstream deps, has downstream consumers | Merges first; downstream blocked until verified |
| Independent | No upstream deps, no downstream consumers | Runs in parallel with Foundation |
| Dependent | Has upstream dependencies | S1–S4 in parallel; S5 blocked until `foundationVerified = true` |

5. **Estimate effort** — expressed as [low]–[high] hours per phase
6. **Recommend developer profiles** — UI-heavy, Backend-heavy, Database, Full-stack, or Any (never names specific developers)

### Team Review and Adjustment

> 🔵 **HUMAN ACTION**  
> The team reviews the proposed breakdown. For each adjustment, the agent checks file ownership conflicts, independence score impact, and tier impact.

### Path Validation

All `scopedFiles` and `requiredReferences` in the manifest are validated against the codebase:

| Status | Meaning |
|--------|---------|
| EXISTS | File found at the declared path |
| NEW | File does not exist but is expected to be created by this phase |
| MISSING | File not found and not declared as new — **blocks manifest finalisation** |

> 🔒 **ENFORCEMENT POINT**  
> The session manifest is not finalised if any path resolves to MISSING. The team must resolve the path (correct it or declare it NEW) before proceeding.

### Finalisation Outputs

On team confirmation:

| Artifact | Details |
|----------|---------|
| Session manifest | `.sage/sessions/[session-id]/session-manifest.md` |
| Active session pointer | `.sage/sessions/active-session.txt` |
| Linear phase issues | One per phase, status: **Pending Approval**, linked by dependency |
| Git worktrees (Sprint only) | One per phase at `C:\Sage\worktrees\[FEATURE_ID]\phase-[N]\` |
| Branch naming | `LIN-[phase-issue-id]-phase-[N]-[kebab-objective]` |

## Worktrees (Sprint Mode Only)

Sprint mode creates isolated git worktrees for each phase so developers work in parallel without branch conflicts.

- **Root path:** `C:\Sage\worktrees\`
- **Feature directory:** `[FEATURE_ID]\`
- **Phase directory:** `phase-[N]\`
- **Branch naming:** `LIN-[phase-issue-id]-phase-[N]-[kebab-objective]`

Mob and Pair modes do not create worktrees. Developers work sequentially in the same repository.

---

## After Kick-off

Phase issues are now at **Pending Approval** in Linear. The next step is [Phase Approval](3.3-Phase-Approval) — the Product Manager and Lead Dev review and approve each phase issue before developers begin S1.
