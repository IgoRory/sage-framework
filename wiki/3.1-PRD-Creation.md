# 3.1 PRD Creation

*This page covers the full process of creating a Product Requirements Document — from initial feature idea to the Linear issue reaching Ready status — and serves the Product Manager.*

| Step | Actor | Skill / Tool | Output |
|------|-------|-------------|--------|
| 1. Start from work item | PM | Linear / ADO | Feature issue reference (LIN-####) |
| 2. Invoke prd-interviewer | PM + Agent | prd-interviewer | Structured interview session |
| 3. Repo preflight | Agent | git + workflow-config.json | Preflight pass/fail |
| 4. Codebase reconnaissance | Agent | File system read | Internal investigation manifest |
| 5. Conduct interview | PM + Agent | prd-interviewer sections 1–6 | Verbatim answer record |
| 6. PM approval gate | PM | APPROVE / REJECT / REDIRECT | Draft generation authorised |
| 7. Generate drafts | Agent | Local write | PRD + Component Spec to `.sage/prds/[FEATURE_ID]/` |
| 8. Run completeness check | PM | prd-completeness-check | Scored assessment report |
| 9. Remediate (if needed) | PM | Manual edits to PRD at `.sage/prds/[FEATURE_ID]/prd.md` | Score ≥ 80 |
| 10. Linear status → Ready | Agent | Linear MCP | Feature issue enters planning cycle |

---

## Starting a PRD

Every PRD starts from a Linear feature issue or Azure DevOps work item. The [prd-interviewer](1.3-Glossary) skill will not proceed without one. The PM invokes the skill with any of:

- "Let's write a PRD"
- "Start a PRD for [feature]"
- Providing a `LIN-####` reference

> 🤖 **AGENT ACTION**  
> prd-interviewer loads the work item from Linear or ADO, extracts title, description, and any pre-existing acceptance criteria.

---

## Step 0 — Repo Preflight

Before any interview question is asked, the agent enforces a mandatory [preflight](1.3-Glossary) check on the workspace repository.

> 🔒 **ENFORCEMENT POINT**  
> Preflight is instruction-enforced by the prd-interviewer skill. It is not hook-enforced — there is no hook script blocking interview tool calls based on branch state.

**Configuration** (from `.sage/workflow-config.json`):

| Field | Value |
|-------|-------|
| `prd.requiredInterviewBranch` | `dev-main` |
| `prd.remoteName` | `origin` |
| `prd.telemetryFile` | `.sage/prd-interview-telemetry.jsonl` |

**Checks performed:**

1. Current branch equals `dev-main`
2. `git fetch origin` succeeds
3. Local branch is not behind the remote tracking branch (`commitsBehind = 0`)
4. Working tree cleanliness — dirty tree produces a warning, not a failure

**On failure:** The agent stops, emits a `prd_preflight` telemetry event with `preflightOutcome: fail`, and tells the PM what to fix (checkout correct branch, pull, rebase).

**PM override:** If the PM explicitly authorises an override (e.g. hotfix branch), the agent records `preflightOutcome: pass`, `override: true`, `overrideReason: "<verbatim>"` and proceeds.

---

## Silent Codebase Reconnaissance

> 🤖 **AGENT ACTION**  
> Before asking the first question, the agent reads the Profitability codebase silently for 2–3 minutes. It does not narrate this process.

The agent examines:
- Stored procedures (`usp_*`) related to the feature area
- Views affected (`vw_BI_AllInstruments`, `Global_Result` for calculation features)
- Existing UI components (for UI features)
- Configuration tables and reference data
- Test files in the feature area

This reconnaissance produces an internal investigation manifest (emitted as a `prd_investigation_manifest` telemetry event) and shapes the specificity of interview questions.

---

## Complexity Tier Classification

After reconnaissance, the agent classifies the feature using the complexity classifier (`references/complexity-classifier.md`). The tier determines:

- Minimum question thresholds for the main interview
- Minimum edge-case questions required in Section 6
- Expected interview duration

The classification is emitted as a `prd_complexity_classified` telemetry event.

---

## The Interview

The interview has six sections. Sections 1, 4, 5a, and 6 always run. Sections 2, 3, and 5b are conditional.

| Section | Phase ID | Topic | Condition |
|---------|----------|-------|-----------|
| 1 | P1 | Feature and capability definition | Always |
| 2 | P2 | Calculation logic | Q1.3 includes (b) |
| 3 | P3 | Allocation methodology | Q1.3 includes (c) |
| 4 | P4 | Acceptance criteria | Always |
| 5a | P5 | Scope boundaries | Always |
| 5b | P6 | UI and UX | Q1.3 includes (a), or UI files found in recon |
| 6 | P7 | Edge cases and constraints | Always — never skip |

> 🔵 **HUMAN ACTION**  
> The PM answers one question at a time. If they cannot answer, the agent parks the question and moves on. Parked questions become explicit TODO items in the PRD draft.

**Key interview rules:**
- One question at a time — never a list
- Answers recorded verbatim, not summarised
- Vague answers probed once with a codebase-specific example before acceptance
- Section 6 (edge cases) covers seven categories systematically and cannot be skipped regardless of feature type

### Park-It Pattern

When the PM cannot answer:
1. Agent notes the question as unresolved
2. Question is flagged as a gap
3. The parked question appears as a TODO in the PRD draft
4. PM can fill it in before running completeness check

---

## Phase-Mapped Telemetry

Every phase boundary emits `prd_phase_started` / `prd_phase_completed` events to `.sage/prd-interview-telemetry.jsonl`. Each event carries:

- `timestamp` (ISO UTC)
- `event` name
- `workflowKind`: `"prd_interview"`
- `phaseId`: `preflight` | `P1`–`P9`
- `linearIssueId`
- `prdRunId` (UUID, consistent across the entire interview run)

---

## PM Approval Gate

After the interview concludes and post-interview verification completes (structured summary, vague-answer flags, coverage check, parked question review):

> 🔵 **HUMAN ACTION**  
> The PM must respond with one of:
> - **APPROVE** — proceed to draft generation
> - **REJECT: [reason]** — restart or revise specific answers
> - **REDIRECT: [direction]** — continue the interview in a different direction

The agent will not generate PRD drafts without an explicit APPROVE.

---

## Output Artifacts

On APPROVE, the agent produces:

| Artifact | Location |
|----------|----------|
| PRD | `.sage/prds/[FEATURE_ID]/prd.md` |
| Component Specification | `.sage/prds/[FEATURE_ID]/component-spec.md` |
| Verbatim answer record | `.sage/prds/[FEATURE_ID]/interview-answers.json` |

## PRD Completeness Check

Once the PM has reviewed and refined the PRD draft, they invoke [prd-completeness-check](1.3-Glossary) to assess readiness for the planning cycle.

### Six Scoring Dimensions (100 total)

| Dimension | Points | Assessment |
|-----------|--------|------------|
| D1 — Requirement coverage | 15 | All requirements as explicit, testable predicates. No vague qualifiers (responsive, appropriate, correctly, seamlessly, efficiently, properly, well). |
| D2 — AC specificity | 15 | Each requirement has at least one agent-evaluable Given/When/Then AC with explicit input, action, and measurable output. |
| D3 — Edge/empty/error state coverage | 15 | Non-happy-path states for every functional area. Return codes -1 through -8 for calculation features. Seven edge-case categories for Tier 2+ features. |
| D4 — Mockup file completeness | 15 | Every screen in the inventory has a declared repo path and the file exists at that path. |
| D5 — UI component specification | 25 | Six elements per component: name/type, functional description, all states with triggers, user interactions, selectable options, data binding. |
| D6 — Out-of-scope clarity | 15 | Explicit exclusion section with precise language a build agent would not implement. |

> [**DIAGRAM PLACEHOLDER — Completeness Scoring Dimensions Radar Chart**]  
> A radar/spider chart with six axes (D1–D6), showing their point allocations (15, 15, 15, 15, 25, 15) and a shaded threshold line at 80/100 aggregate. Each axis labelled with dimension name and max points.

### Pass Threshold

The current pass threshold is **80/100**, read from `workflow-config.json` field `prd.completenessThreshold`. This value is auto-calibrated by the [skill-effectiveness-evaluator](1.3-Glossary) over time.

### On Pass (≥ 80/100)

> 🤖 **AGENT ACTION**  
> The agent updates the Linear feature issue status to **Ready** via Linear MCP. The PRD is eligible for the next planning cycle.

### On Fail (< 80/100)

The agent produces a structured assessment report listing every finding by dimension, with specific deduction amounts. The Linear status is **not** updated. The PM resolves findings and re-runs the check.

---

## Known Gap

> ⚠️ **KNOWN GAP — No hook-enforced gate on PRD completeness threshold.**  
> The prd-completeness-check skill refuses to set the Linear status to Ready if the score is below 80/100. However, this is instruction-enforced only — there is no hook script that blocks downstream processes based on the PRD score. A human could manually set the Linear feature issue status to Ready in Linear without passing the check. Resolving this requires either a webhook-triggered validation on the Linear status change event, or a downstream hook that reads the assessment report before permitting kick-off.
