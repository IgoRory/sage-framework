# 3.4 Review, Merge, and Session Close

*This page covers the post-build process — from PR creation through merge ordering, foundation verification, documentation generation, and session archival — and serves the Lead Dev (primary for merge), Developers (PR creation), and Product Manager (review).*

| Step | Actor | Action | Output |
|------|-------|--------|--------|
| 1. Create PR | Developer | Push branch, open PR on GitHub | PR targeting main |
| 2. CI pipelines | Automated | ADO pipelines trigger on PR | Build/test results |
| 3. Code review | Lead Dev | Review PR | Approval or change requests |
| 4. Merge (Tier 0) | Lead Dev | Squash-merge Foundation + Independent phases | Tier 0 on main |
| 5. Foundation verification | Orchestrator | Run regression suite | `foundationVerified = true` or fail |
| 6. Incorporate upstream (Tier 1+) | Developer | Fetch + merge origin/main, re-run tests | Branch up to date |
| 7. Merge (Tier 1+) | Lead Dev | Squash-merge Dependent phases | All phases on main |
| 8. Documentation | feature-doc-generator | Generate wiki + user guide to `.sage/prds/[FEATURE_ID]/feature-docs/` | Feature documentation |
| 9. Session archival | Lead Dev + Agent | Commit artifacts, clean worktrees | Session closed |

---

## PR Creation

When a developer completes all build steps (S1–S8) for their phase, they create a pull request.

> 🔵 **HUMAN ACTION**  
> Developer commits all phase artifacts, pushes the branch, and opens a PR on GitHub.

**PR requirements:**

| Field | Format |
|-------|--------|
| Base branch | `main` |
| Title | `[FEATURE_ID] Phase N: [objective]` |
| Reviewer | Lead Dev |
| Branch source | `LIN-[phase-issue-id]-phase-[N]-[kebab-objective]` |

The PR contains all source code changes plus phase artifacts from `.sage/sessions/[session-id]/phase-[N]/`.

## CI/CD Pipelines

> 🤖 **AGENT ACTION**  
> Azure DevOps CI/CD pipelines trigger automatically on PRs as normal. No SAGE-specific CI configuration is required.

Three pipelines apply to Profitability PRs:

| Pipeline | Scope |
|----------|-------|
| `profitability-db.yml` | Database changes (stored procedures, views, migrations) |
| `profitability-api.yml` | .NET API changes (services, controllers, models) |
| `profitability-web.yml` | Angular frontend changes (components, services, modules) |

The standard pipeline behaviour applies — build, test, and report results on the PR.

## Merge Order

Merge order follows the tier structure defined in `manifest.sessionState.mergeOrder`.

> 🔒 **ENFORCEMENT POINT**  
> Tier 0 phases (Foundation + Independent) merge first. Tier 1+ phases (Dependent) wait until Foundation verification passes.

| Tier | Phase Types | Merge Condition |
|------|-------------|-----------------|
| 0 | Foundation, Independent | PR approved by Lead Dev, CI green |
| 1+ | Dependent | Tier 0 merged, foundation verification passed, upstream incorporated |

No branch: foundationRegressionResult = fail → Linear violation issue → Dependent phases remain blocked. Label each arrow with the trigger condition.

## Merge Strategy

> 🔵 **HUMAN ACTION**  
> The **Lead Dev** performs all merges to main. Developers do not merge their own PRs.

**Strategy:** Squash and merge.

**Commit message format:**
```
[FEATURE_ID] Phase N: [objective] (#PR-number)
```

This produces a single commit per phase on main, making the history readable and bisectable.

## Foundation Verification

After all Tier 0 phases (Foundation + Independent) reach **Done** in Linear, the [orchestrator](1.3-Glossary) triggers foundation verification.

> 🤖 **AGENT ACTION**  
> The orchestrator monitors Foundation and Independent phase Linear issues. When all reach Done, it runs the regression suite.

### Regression Commands

| Stack | Command |
|-------|---------|
| .NET | `dotnet test --no-build` |
| TypeScript | `npx jest --passWithNoTests` |

### On Pass

1. Orchestrator sets `foundationVerified = true` in the session manifest
2. Dependent phase Linear issues updated to **Foundation Verified**
3. Team notified that Dependent phases are unblocked

> 🔒 **ENFORCEMENT POINT**  
> The `foundation-verified-gate` hook blocks Dependent phases from entering S5 (build) until `foundationVerified = true` in the manifest. This hook fires on `preToolUse` and is blocking.

### On Fail

1. Orchestrator sets `foundationRegressionResult = fail` in the manifest
2. Orchestrator creates a Linear issue with label `violation` assigned to the Lead Dev
3. Dependent phases remain blocked — developers cannot proceed to S5

The Lead Dev must investigate the regression failure, fix it on main, and re-trigger verification.

> [**DIAGRAM PLACEHOLDER — Post-Merge Regression Flow**]  
> A flowchart: All Tier 0 issues at Done → Orchestrator triggers regression → Run dotnet test + npx jest → diamond: All pass? → Yes: set foundationVerified = true, update Dependent issues to Foundation Verified, notify team. No: set foundationRegressionResult = fail, create violation issue in Linear, Dependent phases stay blocked. Show the foundation-verified-gate hook as a lock icon between "Foundation Verified status" and "Dependent phase S5 entry".

## Incorporating Upstream (Tier 1+ Phases)

Before a Dependent phase can be merged, its developer must incorporate the now-merged Foundation code.

> 🔵 **HUMAN ACTION**  
> Developer performs the following on their phase branch:

```bash
git fetch origin
git merge origin/main
# Resolve any conflicts
# Re-run phase tests to confirm no regressions
```

The developer then pushes the updated branch and confirms CI is green before the Lead Dev merges.

## Feature Documentation

After all phases are merged, the [feature-doc-generator](1.3-Glossary) agent generates documentation.

> 🤖 **AGENT ACTION**  
> feature-doc-generator reads completion reports, test results, and the PRD, then writes documentation to `.sage/prds/[FEATURE_ID]/feature-docs/`.

**Outputs:**

| Document | Location |
|----------|----------|
| Technical wiki | `.sage/prds/[FEATURE_ID]/feature-docs/technical-wiki.md` |
| User guide | `.sage/prds/[FEATURE_ID]/feature-docs/user-guide.md` |

**Constraint:** Documentation reflects what was actually built, not what was originally planned. Differences between the PRD and the implementation are documented explicitly.

## Session Archival

Once all phases are merged and documentation is generated, the session is archived.

> 🔵 **HUMAN ACTION**  
> Lead Dev triggers or confirms session archival.

**Archival steps:**

1. **Commit session artifacts** — all files in `.sage/sessions/[FEATURE_ID]/` are committed to main
2. **Push to main** — session record is permanently preserved in the repository
3. **Remove worktrees** — all phase worktrees under `C:\Sage\worktrees\[FEATURE_ID]\` are deleted
4. **Delete remote branches** — all `LIN-[phase-issue-id]-phase-[N]-*` branches are removed from origin
5. **Clear active-session.txt** — `.sage/sessions/active-session.txt` is emptied or deleted

**Permanent record:** The session directory `.sage/sessions/[FEATURE_ID]/` remains in the repository permanently. It contains:

- Session manifest
- Phase breakdown document
- Dev interview summaries
- Implementation plans
- Traceability reviews
- Validation artifacts
- Code review reports
- Test results
- Completion reports
- Kickoff dev review log and phase-splitter briefing (Sprint)

This record supports future [intel-advisor](1.3-Glossary) capacity recommendations and [session-performance-evaluator](1.3-Glossary) scoring.

## End-to-End Phase Status Lifecycle

```
Pending Approval → Approved → In Progress → Build Complete → Done
```

| Transition | Trigger |
|-----------|---------|
| Pending Approval → Approved | PM + Lead Dev approve in Linear |
| Approved → In Progress | Developer begins S1 |
| In Progress → Build Complete | S1–S8 all complete |
| Build Complete → Done | PR merged to main by Lead Dev |
