# S2 — Implementation Plan

The [implementation-planner](1.3-Glossary) agent translates the refined TDD scenarios from S1 into a concrete implementation plan. Every scenario maps to a specific test file and assertion method. Every file to be created or modified is listed with its exact path and purpose.

---

## What the agent reads

- **Dev-interview summary** (`phase-{N}-dev-interview-summary.md`) — refined TDD scenarios, technical decisions, build mode
- **TDD spec** — original Given/When/Then scenarios from [kick-off](3.2-Sprint-Kickoff)
- **[Session manifest](1.3-Glossary)** — `scopedFiles`, `requiredReferences`, phase definition
- **PRD and component specification** — from Notion via MCP
- **Actual codebase files** — reads existing source files to understand current patterns, imports, and structures

---

## What the plan contains

The implementation plan is a structured document with:

1. **Scenario-to-test mapping** — every TDD scenario from the spec maps to a specific test file path and assertion method name. No unmapped scenarios are permitted.
2. **Files to create** — each with its full path and purpose
3. **Files to modify** — each with its full path and a description of the changes
4. **Dependency order** — the sequence in which files should be created/modified
5. **Linear tasks** — the agent populates the phase's Linear issue with granular tasks via MCP

> **🤖 AGENT ACTION** — The implementation-planner reads all inputs, produces the plan, and creates Linear tasks. In Checkpoint mode, it also generates batch definitions and writes them to the session manifest.

---

## Checkpoint mode: batch breakdown

When the developer selected [Checkpoint](1.3-Glossary) build mode at S1, the implementation-planner generates a batch breakdown. Batches follow the `batchBoundaryRules` defined in `workflow-config.json`, which group tasks by layer:

| Phase type | Batch 1 | Batch 2 | Batch 3 |
|---|---|---|---|
| **database** | schema-and-migrations | core-crud-procedures | edge-case-procedures-and-functions |
| **api** | data-models-and-dal | service-layer | controllers-and-endpoints |
| **ui** | component-structure-and-data-binding | state-transitions-and-interactions | error-states-and-edge-cases |
| **full-stack** | database-layer | api-layer | ui-layer |

Each [batch](1.3-Glossary) definition written to the manifest contains:

- `id` — unique batch identifier
- `label` — human-readable name from the boundary rules
- `taskIds` — Linear task IDs assigned to this batch
- `confirmed` — set to `false` (only the developer can set this to `true`)

> **🤖 AGENT ACTION** — The implementation-planner writes batch definitions to the session manifest before exiting. In Autonomous mode, no batch definitions are written.

---

## Enforcement

> **🔒 ENFORCEMENT POINT** — `manifest-step-gate` blocks S2 from starting unless `phase-{N}-dev-interview-summary.md` exists in the phase directory. The dev-interview agent must complete and write its artifact before the implementation-planner can begin.

The implementation-planner is scoped to write only within the current phase directory. It cannot modify files outside this scope.
