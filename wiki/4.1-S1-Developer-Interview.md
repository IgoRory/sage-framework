# S1 — Developer Interview

The Developer Interview is the first step a developer encounters after a [phase](1.3-Glossary) is approved. The [dev-interview](1.3-Glossary) agent asks targeted questions scoped exclusively to the current phase, validates and refines the [TDD spec](1.3-Glossary) scenarios generated at [kick-off](3.2-Sprint-Kickoff), and records the developer's build mode choice.

---

## How to invoke

> **🔵 HUMAN ACTION** — Open Cursor IDE in the phase's worktree (Sprint mode) or the main workspace. Invoke the `dev-interview` agent for the phase. The agent reads the [session manifest](1.3-Glossary) to determine the current phase and its scope.

---

## What the agent reads

The dev-interview agent reads these inputs before asking questions:

- **Session manifest** — current phase definition, scoped files, required references
- **TDD spec for the phase** — Given/When/Then scenarios generated at kick-off
- **PRD from Notion** — product requirements via MCP
- **Prior phase handoff document** — if this is Phase 2 or later, reads the handoff from the preceding phase
- **Codebase scoped files** — actual source files listed in the phase's `scopedFiles`

---

## Question scope

Questions are scoped to the current phase only. The agent does not re-discover requirements — the PRD and TDD spec already exist. Instead, it validates and refines them by asking about implementation specifics:

- **UI phases** — data sources for each field, which fields are editable vs read-only, component state transitions, error display patterns
- **Calculation phases** — exact formulas with specific numbers, rounding rules, null handling, intermediate calculation steps
- **Database phases** — stored procedure names, column types, nullable fields, index strategies, migration approach and constraints
- **API phases** — route patterns, request/response shapes, HTTP status codes, error response formats, authentication requirements
- **Cross-cutting** — migration approach, constraints on existing data, backward compatibility

> **🤖 AGENT ACTION** — The dev-interview agent asks questions one focus area at a time, waits for the developer's response, and refines TDD scenarios based on the answers. It does not move to the next focus area until the current one is resolved.

---

## Build mode selection

At the end of the interview, the agent asks the developer to choose their build mode:

| Mode | Behaviour | Best for |
|---|---|---|
| **[Autonomous](1.3-Glossary)** (default) | Agent completes all tasks end-to-end without pausing. Developer reviews the finished code at S6. | Experienced developers, well-understood phases, straightforward implementations |
| **[Checkpoint](1.3-Glossary)** | Agent completes one batch of tasks, writes a summary, then pauses for developer review before starting the next batch. | Complex phases, unfamiliar domain areas, phases touching critical financial logic |

> **🔵 HUMAN ACTION** — Tell the agent your build mode choice: "Autonomous" or "Checkpoint". The agent records this in the dev-interview summary. If you say nothing, the default is Autonomous.

---

## What the agent produces

The dev-interview agent writes `phase-{N}-dev-interview-summary.md` to the phase directory. This file contains:

- All questions asked and answers received
- TDD scenario refinements (additions, modifications, removals with justification)
- Technical decisions made during the interview
- Build mode selection and rationale

---

## Enforcement

> **🔒 ENFORCEMENT POINT** — `plan-mode-enforcer` blocks ALL file-write tool calls when the manifest's `currentStep` is `dev-interview`. This includes `str_replace_editor`, `write_file`, `create_file`, `apply_diff`, and any other tool that modifies the filesystem. The agent operates in read-only mode for the duration of S1. The only file the agent writes is the dev-interview summary at the end of the step.

> **🔒 ENFORCEMENT POINT** — `phase-approval-gate` blocks S1 from starting until the phase's Linear issue status is "Approved". The Product Manager and Lead Dev must approve the phase in Linear before the developer can begin.
