# S6 — Code Review

The [code-reviewer](1.3-Glossary) agent reviews all code written during S5 against the implementation plan, TDD scenarios, and Profitability domain constraints. It is strictly read-only — it reports findings but never modifies code.

---

## Entry gate

> **🔒 ENFORCEMENT POINT** — `tdd-results-gate` blocks S6 from starting unless `phase-{N}-tdd-results.md` exists in the phase directory AND contains `STATUS: PASS`. Code review cannot begin on code that has failing tests.

---

## Review dimensions

The code-reviewer evaluates the build output across five dimensions:

| Dimension | What the reviewer checks |
|---|---|
| **Code quality** | Adherence to project patterns, readability, maintainability, appropriate abstraction levels |
| **Security** | Input validation, SQL injection vectors, authentication/authorisation enforcement, sensitive data handling |
| **Performance** | Query efficiency at production data volumes, unnecessary iterations, N+1 patterns, missing indexes |
| **Edge case handling** | Null inputs, empty collections, boundary values, concurrent access, missing data scenarios |
| **Error handling** | Unhandled exceptions, generic catch blocks, meaningful error messages, error propagation patterns |

> **🤖 AGENT ACTION** — The code-reviewer reads all source files modified or created during S5, the implementation plan, the TDD spec, the PRD, and the dev-interview summary. It evaluates every file against the five dimensions and classifies each finding.

---

## Finding severities

| Severity | Criteria | Examples |
|---|---|---|
| **Critical** | Security vulnerability, data corruption risk, unhandled exception that could crash the application | SQL injection in a stored procedure parameter. Unvalidated user input written directly to a financial calculation. Missing null check on a required field that would throw at runtime. |
| **Major** | Performance issue at production data volumes, missing PRD error state, logic deviation from the spec | A query that scans the full table without an index on a 10M-row table. PRD requires an error message on allocation failure; code silently swallows the exception. |
| **Minor** | Naming inconsistencies, style deviations, non-functional improvements | Variable named `x` instead of `allocationPercentage`. Inconsistent casing between related files. |

---

## The Critical findings line

The code review document must contain the following exact line:

```
Critical findings: N
```

Where `N` is the integer count of Critical-severity findings. This format is machine-read by the [code-review-gate](6.2-Enforcement-Reference).

> **🔒 ENFORCEMENT POINT** — `code-review-gate` blocks S7 from starting unless `phase-{N}-code-review.md` contains the exact substring `Critical findings: 0`. If any Critical findings are present, S7 cannot proceed.

---

## What happens when Critical findings are found

When the code-reviewer reports Critical findings:

1. The `code-review-gate` blocks S7 entry
2. The developer reads the code review findings
3. The build agent addresses each Critical finding — fixing the code and re-running tests
4. After fixes, S5 TDD results are re-confirmed (`STATUS: PASS`)
5. The code-reviewer re-runs S6
6. The cycle repeats until `Critical findings: 0`

Major and Minor findings are recorded for the developer's awareness. They do not block progression to S7.

---

## What the agent cannot do

The code-reviewer never modifies code. It does not suggest fixes inline, does not apply patches, and does not alter test files. It reports what it finds. The build agent (at S5) is responsible for addressing Critical findings if a re-run is needed.
