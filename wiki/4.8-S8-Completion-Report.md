# S8 — Completion Report

S8 generates the completion report for the phase and posts it to the phase's [Linear](1.3-Glossary) issue. This step exists because of a specific enforcement requirement: the agent must not be able to declare a phase complete without evidence that tests passed.

---

## The stop-gate

The `completion-report-stop-gate` is the hardest gate in the framework. It is structurally different from every other gate:

> **🔒 ENFORCEMENT POINT** — `completion-report-stop-gate` fires on the **`stop` event**, not on `preToolUse`. This means the agent literally cannot finish its conversation turn until `phase-{N}-test-results.md` exists in the phase directory AND contains `STATUS: PASS`. Every other gate blocks a tool call. This gate blocks the agent from stopping.

This gate was designed as a structural fix for a past failure where an agent declared a phase complete without running tests. The stop-gate makes that impossible at the execution layer.

The gate fires during three steps: `completion-report`, `agent-testing`, and `build`. In all three contexts, the agent cannot end its turn without test evidence.

---

## What the completion report contains

The agent generates `phase-{N}-completion-report.md` with:

| Section | Contents |
|---|---|
| **What was built** | Summary of components, services, procedures, or UI elements created or modified |
| **Test results summary** | Pass/fail counts, coverage areas, gap-analyzer additions |
| **Deviations from plan** | Any changes made during S5 that were not in the implementation plan, with justification |
| **Deferred items** | Anything identified during the build that was out of scope and deferred to a future phase or feature |

> **🤖 AGENT ACTION** — The agent reads the implementation plan, TDD results, test results, code review, and any batch reviews (Checkpoint mode). It compiles the completion report and writes it to the phase directory. It then posts the report contents to the phase's Linear issue via MCP.

---

## What happens after S8

After the completion report is written and posted:

1. The agent's turn ends (the stop-gate permits this because test evidence exists)
2. The developer creates a pull request from the phase's worktree branch

> **🔵 HUMAN ACTION** — Create a PR from the phase worktree branch to main. The process then moves to [Review, Merge, and Session Close](3.4-Review-Merge-Session-Close), where the Lead Dev manages merge order based on [phase type](1.3-Glossary) and tier.

---

## Why the stop-gate matters

Most gates operate on `preToolUse` — they block a specific tool call. An agent blocked by a `preToolUse` gate can still end its turn and claim to be done. The stop-gate closes this gap.

Without the stop-gate, the following failure mode is possible:
1. Agent reaches S8
2. Agent writes a completion report without running S7 tests
3. Agent ends its turn
4. No gate fires because no tool call was blocked — the agent simply stopped

With the stop-gate:
1. Agent reaches S8
2. Agent attempts to end its turn
3. The `stop` event fires
4. The hook checks for `phase-{N}-test-results.md` with `STATUS: PASS`
5. If the file does not exist or does not contain `STATUS: PASS`, the agent is blocked from stopping
6. The agent must go back and ensure tests are run and passing before it can finish

This makes the stop-gate the structural last line of defence in the build pipeline.

---

## Enforcement

> **🔒 ENFORCEMENT POINT** — `completion-report-stop-gate` fires on the `stop` event. Blocks the agent from ending its turn unless `phase-{N}-test-results.md` exists AND contains `STATUS: PASS`. This is the only gate in SAGE that fires on `stop` rather than `preToolUse`.
