# SAGE Intel — Delivery Metrics and Planning

SAGE Intel replaces human estimation with empirical delivery data. The [intel-recorder](6.3-Agent-Catalogue) collects and stores metrics after every completed work cycle. The [intel-advisor](6.3-Agent-Catalogue) reads that data to answer planning questions — sprint scope, release dates, capacity — using mode-specific calibration. No human estimation is used at any stage.

---

## intel-recorder

The intel-recorder runs automatically after every work cycle, immediately following the [session-performance-evaluator](5.1-SAGE-Hone-Session-Performance). It reads the [session manifest](6.1-Session-Manifest-Reference), completion reports, [telemetry](6.5-Telemetry-Reference), Linear timestamps, and git PR diff data.

### Per-phase metrics collected

| Metric | Source | Notes |
|---|---|---|
| Workflow [mode](1.3-Glossary) | Session manifest header | mob, sprint, pair, solo |
| Layer | Phase definition | ui, backend, data, full-stack |
| Phase type | Phase definition | foundation, independent, dependent |
| Estimated hours | Phase definition `effortEstimateHours` | Low/high range |
| Actual hours | Completion log `actualDurationHours` | Mob mode: team-hours (participants × elapsed), not individual hours |
| Build mode | Phase runtime | autonomous or checkpoint |
| S1–S8 durations | Step timestamps | Per-step elapsed time |
| [Hook](1.3-Glossary) rejections | Telemetry `hook_rejection` events | Count per phase |
| TDD first-pass rate | `phase-{N}-tdd-results.md` analysis | Percentage of RGR cycles passing GREEN on first attempt |
| S7 pass rate | `phase-{N}-test-results.md` | Pass/fail on first S7 run |
| S6 critical findings | `phase-{N}-code-review.md` | Count of Critical findings |
| Foundation wait time | Step timestamps for [Dependent](1.3-Glossary) phases | Time between phase readiness and `foundationVerified` |
| Approval turnaround | Linear timestamps | **Internal only — NEVER published to leadership** |

### Outputs

> 🤖 **AGENT ACTION** — intel-recorder writes the following after each cycle:

| Output | Location | Format |
|---|---|---|
| Velocity history | `.sage/intel/velocity-history.jsonl` | One JSON entry per completed phase, tagged with workflow mode |
| Release history | `.sage/intel/release-history.jsonl` | One entry per completed release |
| Mode calibration datasets | `mob_calibration.json`, `sprint_calibration.json`, `pair_calibration.json` | Regenerated from full history each cycle — never incremental |
| Notion metrics dashboard | Notion (via MCP) | Updated dashboard page |
| Linear metric comments | Linear (via MCP) | Summary comment on feature issues |

### Calibration rules

- Calibration datasets are maintained **per workflow mode** — Mob and Sprint data are never blended
- Datasets are **regenerated from the full velocity history** on every cycle, not updated incrementally
- This ensures calibration reflects the complete historical dataset, not a running average that can drift

## intel-advisor

The [intel-advisor](6.3-Agent-Catalogue) is a foreground, read-only agent invoked on demand during planning. It reads `.sage/intel/velocity-history.jsonl` and the mode-specific calibration dataset to answer questions.

### Invocation

Type exactly:
> *"Please run intel-advisor — [weekly planning / release date estimate for [release name] / scope change: [feature name] added or removed]"*

### Three query modes

**1. Weekly planning**
Recommends features to pull into the work cycle, ranked by fit given current developer availability and in-flight work. Considers: features at Ready status in Linear, in-flight phases, estimated effort per feature by layer composition, and available developer capacity.

**2. Release date estimation**
Produces P50 and P80 estimated completion dates for the release's feature set, with a confidence band and a status indicator:

| Indicator | Meaning |
|---|---|
| **On Track** | P80 date is on or before the release target |
| **At Risk** | P50 is before target but P80 is after |
| **Delayed** | P50 is after the release target |

**3. Scope change analysis**
For a feature added to a release: revised P50/P80 estimates and what would need to move out to maintain the current release date. For a feature removed: revised estimates and what could fill the freed capacity.

### Confidence levels

The advisor's confidence depends on how many completed phases exist in the calibration dataset for the relevant layer type and workflow mode:

| Sample count (per layer type, per mode) | Confidence level | Behaviour |
|---|---|---|
| Fewer than 5 | Very low | Uses heuristic estimates from [phase-splitter](6.4-Skill-Catalogue) with explicit warning |
| 5–9 | Moderate | Standard estimation |
| 10–19 | Good | Standard estimation |
| 20 or more | High | Standard estimation |

> [**DIAGRAM PLACEHOLDER — Confidence Level Progression**]
>
> A horizontal bar or step chart showing four confidence bands (Very low, Moderate, Good, High) mapped to sample counts (<5, 5–9, 10–19, 20+). The Very low band is marked with a warning icon and the label "heuristic fallback." Each band is wider as sample count grows, conveying that confidence increases with data.

The advisor uses **mode-specific calibration only**. Mob estimates draw from `mob_calibration.json`, Sprint from `sprint_calibration.json`. Modes are never mixed.

The advisor **never asks for human estimates**. When data is insufficient (Very low confidence), it flags the low confidence explicitly and uses heuristics — it does not prompt the user for a guess.
