*This page is the complete reference for all twelve hook scripts that enforce the SAGE workflow — what each checks, when it fires, and how to recover from a block. It serves developers troubleshooting gate rejections and the Lead Dev for enforcement oversight.*

---

# Enforcement Reference — All Gates

SAGE enforces its workflow through twelve [hook](1.3-Glossary) scripts registered in `hooks.json`. Each hook intercepts specific Cursor IDE events and either logs or blocks the action based on a condition it evaluates. Blocking hooks write to stderr with the prefix `🔴 GATE BLOCKED` and emit a `hook_rejection` event to [telemetry](6.5-Telemetry-Reference).

| Behaviour | Count | Hooks |
|---|---|---|
| **Blocking** | 10 | plan-mode-enforcer, manifest-step-gate, phase-approval-gate, required-references-gate, validation-confirmed-gate, foundation-verified-gate, batch-confirmation-gate, tdd-results-gate, code-review-gate, completion-report-stop-gate |
| **Non-blocking** | 2 | telemetry-logger, skill-update-trigger-watcher |

---

## 1. telemetry-logger

| | |
|---|---|
| **ID** | `telemetry-logger` |
| **Blocking** | No |
| **Events** | `preToolUse`, `afterFileEdit`, `beforeShellExecution`, `afterShellExecution`, `afterMCPExecution`, `stop` |
| **Script** | `telemetry_logger.py` |
| **Timeout** | 2000ms |

**What it does:** Writes every hook event to `workflow-telemetry.jsonl` at the session root. Always runs. Never blocks. Logging failures do not affect gate behaviour.

**Applies to:** All agents, all steps.

**Telemetry record fields:** `hook_event_name`, `recorded_at`, `phase`, `step`, `active_agent`, `conversation_id`, plus event-specific data (`tool_name`, `file_path`, `command`, `exit_code`, `mcp_tool`, etc.).

## 2. plan-mode-enforcer

| | |
|---|---|
| **ID** | `plan-mode-enforcer` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `plan_mode_enforcer.py` |
| **Timeout** | 3000ms |

**What it checks:** Is the [session manifest](6.1-Session-Manifest-Reference) `currentStep` set to `dev-interview`? If yes, is the tool call a file-write operation?

**Pass condition:** Tool call is a read operation, OR `currentStep` is not `dev-interview`.

**Fail behaviour:** `🔴 GATE BLOCKED — File writes are blocked during S1 (Developer Interview). Plan mode is enforced by the plan-mode-enforcer hook.`

**Telemetry on block:** `hook_rejection` event with `gate: plan-mode-enforcer`, `tool_name`, `phase`, `step: dev-interview`.

**Applies to:** [dev-interview](6.3-Agent-Catalogue) agent during S1.

**Recovery:** No recovery action needed — the gate is working as designed. The [dev-interview](6.3-Agent-Catalogue) agent operates in read-only mode during S1. File writes become available at S2.

## 3. manifest-step-gate

| | |
|---|---|
| **ID** | `manifest-step-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `manifest_step_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Does the prior step's required [artifact](1.3-Glossary) exist in the phase directory? For S3: also checks `Blocker findings: 0` in the traceability review.

**Pass condition:** Prior step's artifact file exists and (where applicable) contains the required content.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot proceed to [step]. Required artifact from [prior step] not found: [expected file path].`

**Telemetry on block:** `hook_rejection` event with `gate: manifest-step-gate`, `missing_artifact`, `current_step`, `required_step`.

**Applies to:** All agents, all step transitions (S1→S2, S2→S3, ... S7→S8).

**Recovery:** Complete the prior step. The artifact must exist at the expected path with the required content.

---

## 4. phase-approval-gate

| | |
|---|---|
| **ID** | `phase-approval-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `phase_approval_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Is the phase's Linear issue status `Approved` (or `Foundation Verified` for Sprint mode)?

**Pass condition:** Linear issue status is `Approved` or a downstream status.

**Fail behaviour:** `🔴 GATE BLOCKED — Phase [N] Linear issue [LIN-####] is not yet Approved. Current status: [status]. Build work cannot begin until the PM and Lead Dev approve the phase.`

**Telemetry on block:** `hook_rejection` event with `gate: phase-approval-gate`, `linear_issue_id`, `current_status`.

**Applies to:** All agents at S1 entry.

> 🔵 **HUMAN ACTION** — The PM and Lead Dev must approve the phase issue in Linear before build work can begin.

**Recovery:** Move the Linear phase issue to `Approved` status.

---

## 5. required-references-gate

| | |
|---|---|
| **ID** | `required-references-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `required_references_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Have all files listed in `phases[N].definition.requiredReferences` been read in the current session? Confirmed via `read_file` events in [telemetry](6.5-Telemetry-Reference).

**Pass condition:** Every file in `requiredReferences` has a corresponding `read_file` telemetry event.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot begin S5 build. The following required reference files have not been read: [list of unread files].`

**Telemetry on block:** `hook_rejection` event with `gate: required-references-gate`, `unread_files`.

**Applies to:** Build agents at S5 entry.

**Recovery:** Read the listed files. The gate checks telemetry for `read_file` events, so the files must be read in the current Cursor session.

---

## 6. validation-confirmed-gate

| | |
|---|---|
| **ID** | `validation-confirmed-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `validation_confirmed_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Is `phases[N].runtime.validationConfirmed` set to `true` in the session manifest?

**Pass condition:** `validationConfirmed === true`.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot begin S5 build. validationConfirmed is false for phase [N]. The developer must review the validation artifact and set validationConfirmed = true in the session manifest.`

**Telemetry on block:** `hook_rejection` event with `gate: validation-confirmed-gate`, `phase`.

**Applies to:** Build agents at S5 entry.

> 🔵 **HUMAN ACTION** — The developer must open the session manifest, find `phases[N].runtime.validationConfirmed`, change `false` to `true`, and save. No agent can set this flag.

**Recovery:** Edit the manifest manually. See [S4 — Plan Validation](4.4-S4-Plan-Validation).

## 7. foundation-verified-gate

| | |
|---|---|
| **ID** | `foundation-verified-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `foundation_verified_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Is `sessionState.foundationVerified` set to `true`? Only applies to phases with `phaseType: dependent`.

**Pass condition:** `foundationVerified === true`, OR the phase is not `dependent`.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot begin S5 for dependent phase [N]. Foundation phases have not been verified. foundationVerified is false.`

**Telemetry on block:** `hook_rejection` event with `gate: foundation-verified-gate`, `phase`, `phase_type: dependent`.

**Applies to:** Build agents on [Dependent](1.3-Glossary) phases at S5 entry.

> 🔒 **ENFORCEMENT POINT** — The [orchestrator](6.3-Agent-Catalogue) sets `foundationVerified = true` after all Foundation and Independent phases have merged and post-merge regression has passed. No developer action is required — this is an agent-to-gate handoff.

**Recovery:** Wait for Foundation phase merge and regression to complete.

## 8. batch-confirmation-gate

| | |
|---|---|
| **ID** | `batch-confirmation-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `batch_confirmation_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** In [Checkpoint](1.3-Glossary) build mode only: is `batches[currentBatchId].confirmed` set to `true`?

**Pass condition:** `confirmed === true` for the current batch, OR build mode is `autonomous` (gate does not apply).

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot proceed to batch [N+1]. The developer has not confirmed batch [N]. Set batches[N].confirmed = true in the session manifest after reviewing the batch review document.`

**Telemetry on block:** `hook_rejection` event with `gate: batch-confirmation-gate`, `batch_id`, `phase`.

**Applies to:** Build agents in Checkpoint mode between batches.

> 🔵 **HUMAN ACTION** — The developer reviews the batch output, then sets `batches[N].confirmed = true` in the session manifest.

**Recovery:** Edit the manifest to confirm the current batch.

---

## 9. tdd-results-gate

| | |
|---|---|
| **ID** | `tdd-results-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `tdd_results_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Does `phase-{N}-tdd-results.md` exist in the phase directory and contain `STATUS: PASS`?

**Pass condition:** File exists AND contains the line `STATUS: PASS`.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot begin S6 code review. phase-{N}-tdd-results.md does not exist or does not contain STATUS: PASS.`

**Telemetry on block:** `hook_rejection` event with `gate: tdd-results-gate`, `phase`, `file_status`.

**Applies to:** [code-reviewer](6.3-Agent-Catalogue) at S6 entry.

**Recovery:** Complete S5 build with all TDD tests passing. The [test-runner](6.3-Agent-Catalogue) writes `STATUS: PASS` to `phase-{N}-tdd-results.md`.

## 10. code-review-gate

| | |
|---|---|
| **ID** | `code-review-gate` |
| **Blocking** | Yes |
| **Event** | `preToolUse` |
| **Script** | `code_review_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Does `phase-{N}-code-review.md` exist and contain `Critical findings: 0`?

**Pass condition:** File exists AND contains `Critical findings: 0`.

**Fail behaviour:** `🔴 GATE BLOCKED — Cannot begin S7 agent testing. Code review has Critical findings. Resolve all Critical findings before proceeding.`

**Telemetry on block:** `hook_rejection` event with `gate: code-review-gate`, `phase`, `critical_count`.

**Applies to:** [test-runner](6.3-Agent-Catalogue) at S7 entry.

**Recovery:** Resolve all Critical findings from S6 code review. The [code-reviewer](6.3-Agent-Catalogue) must re-run and produce `Critical findings: 0`.

## 11. completion-report-stop-gate

| | |
|---|---|
| **ID** | `completion-report-stop-gate` |
| **Blocking** | Yes |
| **Event** | `stop` |
| **Script** | `completion_report_stop_gate.py` |
| **Timeout** | 3000ms |

**What it checks:** Does `phase-{N}-test-results.md` exist and contain `STATUS: PASS`?

**Pass condition:** File exists AND contains `STATUS: PASS`.

**Fail behaviour:** `🔴 GATE BLOCKED — Agent cannot end turn. phase-{N}-test-results.md does not contain STATUS: PASS. Testing must complete with a passing status before the phase can close.`

**Telemetry on block:** `hook_rejection` event with `gate: completion-report-stop-gate`, `phase`.

**Applies to:** All agents at S8 — prevents an agent from ending its turn until test results confirm a pass.

**Recovery:** S7 testing must complete with `STATUS: PASS` written to the test results file.

## 12. skill-update-trigger-watcher

| | |
|---|---|
| **ID** | `skill-update-trigger-watcher` |
| **Blocking** | No |
| **Events** | `afterFileEdit` |
| **Script** | `skill_update_trigger_watcher.py` |
| **Timeout** | 5000ms |

**What it does:** Detects new `.json` trigger files written to `.skill-update-triggers/` by the Linear webhook receiver. When a trigger file is detected, fires the [skill-effectiveness-evaluator](6.3-Agent-Catalogue) apply step.

**Applies to:** Background process, not tied to a specific step or agent.

See [SAGE Hone — Skill Improvement](5.2-SAGE-Hone-Skill-Improvement) for the full trigger chain.

## Gate rejection summary

Every blocking gate follows the same pattern:

1. Hook intercepts the tool call or stop event
2. Hook reads the condition from the [session manifest](6.1-Session-Manifest-Reference) or a phase artifact
3. If the condition is not met:
   - Writes `🔴 GATE BLOCKED — [message]` to stderr
   - Writes a `hook_rejection` event to [telemetry](6.5-Telemetry-Reference)
   - Returns a blocking response — the tool call does not execute
4. If the condition is met: the hook returns silently and the tool call proceeds
