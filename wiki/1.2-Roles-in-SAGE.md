# Roles in SAGE

Three teams use SAGE. Each has a different scope of responsibility, and the documentation reflects those differences accurately rather than manufacturing false symmetry.

---

## Product Team

**Members:** Product Manager, Technical Product Manager, Business Analyst

**Owns:**
- Authoring and maintaining product requirements documents (PRDs) using the [`prd-interviewer`](3.1-PRD-Creation) skill
- Running [`prd-completeness-check`](3.1-PRD-Creation) to confirm a feature is ready for planning
- Facilitating the [Sprint Kick-off](3.2-Sprint-Kickoff) and [Mob Kick-off](3.2-Sprint-Kickoff) sessions
- Conducting the [Feature Walkthrough](3.2-Sprint-Kickoff) for Mob mode (required) and Sprint mode (optional)
- Approving phase breakdowns in Linear before the build sprint begins
- Reviewing completion reports and confirming product correctness before [Review & Merge](3.4-Review-Merge-Session-Close)
- Approving skill updates for `prd-interviewer` and `prd-completeness-check` via [SAGE Hone](5.2-SAGE-Hone-Skill-Improvement)
- Running [`intel-advisor`](5.3-SAGE-Intel) at the weekly planning cycle and for release forecasting

**Does not:**
- Configure environments or developer machines
- Interact with the hook enforcement system directly
- Make build execution decisions (Autonomous vs Checkpoint)
- Write code or execute build steps

**Key wiki pages:** [PRD Creation](3.1-PRD-Creation), [Sprint Kick-off](3.2-Sprint-Kickoff), [Phase Approval](3.3-Phase-Approval), [SAGE Intel](5.3-SAGE-Intel)

## Development Team

**Members:** Lead Developer, Developers

### Lead Developer

**Owns:**
- Implementing and maintaining the SAGE framework on the Profitability codebase
- Reviewing and merging pull requests in dependency order during [Review & Merge](3.4-Review-Merge-Session-Close)
- Approving phase breakdowns in Linear alongside the Product Manager
- Approving skill updates for `phase-splitter` and all execution-layer skills via [SAGE Hone](5.2-SAGE-Hone-Skill-Improvement)
- Reviewing session performance reports and acting on systematic violation flags
- Maintaining the framework's technical configuration, hook scripts, and [environment setup](7.1-Environment-Setup)
- Performing all merges to `main` (branch protection enforces this)

### Developers

**Own:**
- Running the [S1–S8 build cycle](4.0-Build-Steps-Overview) on assigned phases during Sprint and Solo builds
- Acting as Driver or Navigator in Mob mode sessions
- Choosing [Autonomous or Checkpoint build mode](4.1-S1-Developer-Interview) at S1
- Confirming the [validation mockup](4.4-S4-Plan-Validation) at S4 by editing the session manifest
- Confirming [batch completions](4.5-S5-Build) in Checkpoint mode by editing the session manifest
- Posting completion reports to phase issues at S8
- Creating pull requests from phase worktrees after S8

**Key wiki pages:** [Build Steps Overview](4.0-Build-Steps-Overview), [S1](4.1-S1-Developer-Interview) through [S8](4.8-S8-Completion-Report), [Environment Setup](7.1-Environment-Setup)

## QA Team

**Members:** QA Team Lead, QA Engineers, Automation Engineers

**Current scope:** The QA team has a more limited role in the current implementation than the other two teams. The automated testing step (S7) is agent-driven; QA does not gate it. The `humanQAGate` feature flag in `workflow-config.json` is currently set to `false`.

**What QA does today:**
- Reviews completion reports and test results asynchronously after build phases complete
- Contributes to capacity planning discussions informed by [SAGE Intel](5.3-SAGE-Intel) data
- Maintains Azure DevOps test plans that run alongside SAGE's agent testing (see [S7 — Agent Testing](4.7-S7-Agent-Testing) for the ADO handoff process)

**What QA does not do today:**
- Gate any step in the S1–S8 sequence
- Run or approve agent testing (S7)
- Block Review & Merge

**Future expansion:** The framework is architecturally designed to accommodate a more active QA role. The `humanQAGate` flag in `workflow-config.json` exists specifically for this purpose — when set to `true`, it would add a QA approval gate to the workflow. That gate is not currently required, and its procedural documentation will be added when it is activated.

**Key wiki pages:** [S7 — Agent Testing](4.7-S7-Agent-Testing), [SAGE Intel](5.3-SAGE-Intel)

## Decisions each role makes

| Decision | Who decides | Where it happens |
|---|---|---|
| Which feature to build next | Product Manager (informed by [intel-advisor](5.3-SAGE-Intel)) | Planning cycle |
| Which workflow mode to use | Product Manager and Lead Dev | Planning cycle |
| Phase breakdown and scope | Team at kick-off, confirmed by Product Manager and Lead Dev | [Kick-off](3.2-Sprint-Kickoff) |
| Developer assignment to phases | Team at kick-off | [Kick-off](3.2-Sprint-Kickoff) |
| Whether a phase is approved to begin | Product Manager and Lead Dev | [Linear approval](3.3-Phase-Approval) |
| Autonomous vs Checkpoint build mode | Developer assigned to the phase | [S1 Developer Interview](4.1-S1-Developer-Interview) |
| Whether the validation mockup is correct | Developer assigned to the phase | [S4 Plan Validation](4.4-S4-Plan-Validation) |
| Whether a Checkpoint batch is acceptable | Developer assigned to the phase | [S5 Build](4.5-S5-Build) |
| Merge order and timing | Lead Dev | [Review & Merge](3.4-Review-Merge-Session-Close) |
| Whether to approve a skill update | Product Manager (PRD skills) or Lead Dev (other skills) | [SAGE Hone](5.2-SAGE-Hone-Skill-Improvement) |
