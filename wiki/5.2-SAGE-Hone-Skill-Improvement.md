# SAGE Hone — Skill Improvement

SAGE Hone's skill improvement pipeline analyses execution patterns across multiple work cycles, identifies skills that consistently underperform against defined criteria, proposes targeted changes, and applies those changes only after human approval. No skill file is ever modified without an approved [Linear](1.3-Glossary) issue.

---

## skill-effectiveness-evaluator

The [skill-effectiveness-evaluator](6.3-Agent-Catalogue) runs every 5 completed work cycles, controlled by `telemetry.skillEvaluationCycleInterval` in `workflow-config.json`.

### Qualification

A skill must have been invoked in at least 3 of the 5 sessions in the evaluation window to qualify. Skills invoked fewer than 3 times do not have enough data to distinguish signal from noise.

### Evaluation

The evaluator reads `workflow-telemetry.jsonl` across the 5-session window and scores each qualifying skill against per-skill criteria defined in `references/per-skill-criteria.md`. When a skill shows consistent underperformance, the evaluator proposes a change.

### Change limits

| Constraint | Limit |
|---|---|
| Maximum changes per skill per cycle | 3 |
| Maximum threshold movement per cycle | 5 points (e.g. cannot shift a scoring threshold from 70 to 80 in one proposal) |
| Minimum evidence required | 3 sessions |
| Rejection suppression | 2 evaluation cycles (10 sessions) |

Rejected changes are written to `skill-update-history.jsonl` with status `rejected`. The evaluator suppresses re-proposal of the same change for 2 evaluation cycles before it can be raised again.

> 🤖 **AGENT ACTION** — The evaluator writes a unified diff to `.skill-update-staging/[LIN-issue-id]-diff.md` and creates a Linear issue with label `skill-update` at status `Pending Approval`.

### Approval routing

| Skill | Approver |
|---|---|
| prd-completeness-check | Product Manager |
| prd-interviewer | Product Manager |
| phase-splitter | Lead Dev |
| All other skills | Lead Dev |

## prd-interviewer-effectiveness-evaluator

The [prd-interviewer-effectiveness-evaluator](6.3-Agent-Catalogue) is a specialised evaluator that focuses exclusively on the [prd-interviewer](6.4-Skill-Catalogue) skill. It uses PRD-specific telemetry rather than general workflow telemetry.

### Data sources

- `.sage/prd-interview-telemetry.jsonl` (path from `prd.telemetryFile` in workflow-config.json)
- Optional [traceability-review](1.3-Glossary) artifacts (to assess whether interview gaps led to downstream traceability findings)
- `skill-update-history.jsonl` (to check suppression state)

### Mutual exclusion

When the prd-interviewer-effectiveness-evaluator is deployed, the skill-effectiveness-evaluator must **skip** prd-interviewer evaluation. Both evaluators cannot propose changes to the same skill — this prevents duplicate Linear issues and conflicting diffs.

### Governance

The prd-interviewer-effectiveness-evaluator follows the same governance as the general evaluator: staged diffs in `.skill-update-staging/`, Linear issue at `Pending Approval`, Product Manager as approver. Minimum 3 completed PRD interview runs before proposing changes. Rejection suppression of 2 cycles aligns with `skillUpdates.suppressionCycles`.

## The apply step — polling trigger chain

When an approver moves a `skill-update` Linear issue to `Approved`, the following chain executes:

### Step-by-step

1. **Linear issue moves to Approved**

> 🔵 **HUMAN ACTION** — The approver (PM or Lead Dev) reviews the staged diff and moves the Linear issue from `Pending Approval` to `Approved`.

2. **Poller detects status change**

> 🤖 **AGENT ACTION** — `skill_update_poller.py` queries Linear via the GraphQL API (using `LINEAR_API_KEY`) for `skill-update` issues with state `Approved` or `Rejected` since the last poll. On match, writes a trigger file to `.skill-update-triggers/LIN-[id]-approved.json` using camelCase keys.

3. **Hook detection**

> 🔒 **ENFORCEMENT POINT** — `skill-update-trigger-watcher` (non-blocking, afterFileEdit event) detects the new trigger file in `.skill-update-triggers/` and fires the evaluator's apply step.

4. **Diff application**

> 🤖 **AGENT ACTION** — The evaluator reads the exact staged diff from `.skill-update-staging/[LIN-issue-id]-diff.md`, applies the changes to the target SKILL.md, and commits with message: `skill-update([skill-name]): [summary]`.

5. **Status update**

> 🤖 **AGENT ACTION** — Linear issue status → `Applied`. An entry is written to `skill-update-history.jsonl` with status `applied`, the diff content, and timestamp.

### Rejection flow

If the approver moves the issue to `Rejected—recorded`, the poller writes a rejection trigger file. The evaluator reads it, writes a `rejected` entry to `skill-update-history.jsonl`, and begins the 2-cycle suppression window.

### Setup

No webhook, ngrok, or signing secret required. Prerequisites:

1. `LINEAR_API_KEY` environment variable set (same key used by Linear MCP)
2. Run `python .cursor/hooks/scripts/skill_update_poller.py` manually, or `--loop 60` for continuous polling
