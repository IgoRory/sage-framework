# 2.1 The Session Lifecycle

*Describes the complete path a feature travels from backlog entry through delivery and post-cycle evaluation, for developers, Product Managers, and Lead Devs working within the SAGE framework.*

| Stage | Session state | Key agents / skills | Primary gate |
|---|---|---|---|
| PRD creation | _(pre-session)_ | [prd-interviewer](1.3-Glossary), [prd-completeness-check](1.3-Glossary) | Score ≥ 80/100 |
| Planning cycle | _(pre-session)_ | [intel-advisor](1.3-Glossary), Product Manager | Mode selected, developers allocated |
| Kick-off + approval | `kick-off` → `build-sprint` | [orchestrator](1.3-Glossary), [kickoff-dev-review](1.3-Glossary), [phase-splitter](1.3-Glossary) | [Session manifest](1.3-Glossary) generated, all phases Approved |
| Build | `build-sprint` | Per-phase agents (S1–S8), [sprint-coordinator](1.3-Glossary) (Sprint only) | All phases reach Build Complete |
| Review & merge | `review-merge` | [orchestrator](1.3-Glossary), [gap-analyzer](1.3-Glossary), [feature-doc-generator](1.3-Glossary) | Regression passes on merged code |
| Post-cycle | `complete` | [session-performance-evaluator](1.3-Glossary), [skill-effectiveness-evaluator](1.3-Glossary), [intel-recorder](1.3-Glossary) | Metrics recorded to `.sage/intel/velocity-history.jsonl` |

## PRD creation

Before a session exists, the feature must have a complete PRD.

> 🔵 HUMAN ACTION
>
> The Product Manager starts a PRD interview by providing a Linear feature issue or ADO work item reference. The feature issue enters the state **PRD In Progress**.

> 🤖 AGENT ACTION
>
> The [prd-interviewer](1.3-Glossary) skill conducts a structured interview across phases P1–P9. It performs codebase reconnaissance before the first question, classifies feature complexity, and asks questions one at a time. On PM approval, it generates a PRD draft and companion Component Specification to `.sage/prds/[FEATURE_ID]/`.

> 🔵 HUMAN ACTION
>
> The PM reviews and refines the draft, then runs [prd-completeness-check](1.3-Glossary) when ready. The feature issue moves to **PRD Under Review**.

> 🤖 AGENT ACTION
>
> [prd-completeness-check](1.3-Glossary) scores the PRD across six dimensions (requirement coverage, AC specificity, edge/empty/error state coverage, mockup file completeness, UI component specification, out-of-scope clarity). Total: 100 points. The pass threshold is read from `prd.completenessThreshold` in `workflow-config.json` (currently 80/100; auto-calibrated over time by [skill-effectiveness-evaluator](1.3-Glossary)).

> 🔒 ENFORCEMENT POINT
>
> If the score is below threshold, the Linear feature issue status is **not** updated. The skill produces a dimension-by-dimension remediation report. The PM must resolve all findings and re-run the check. If the score meets threshold, the feature issue moves to **Ready**.

### Linear feature issue states during PRD creation

**Backlog** → **PRD In Progress** → **PRD Under Review** → **Ready**

## Planning cycle

> 🔵 HUMAN ACTION
>
> The Product Manager or Lead Dev selects a [workflow mode](1.3-Glossary) for the feature: [mob](1.3-Glossary), [sprint](1.3-Glossary), [pair](1.3-Glossary), or [solo](1.3-Glossary). See [2.2 Workflow Modes](2.2-Workflow-Modes) for selection criteria.

> 🤖 AGENT ACTION
>
> [intel-advisor](1.3-Glossary) reads historical delivery data from `.sage/intel/velocity-history.jsonl`, filtered to the selected mode. It produces a capacity advisory report with velocity baselines, phase estimates, recommended developer allocation, and explicit confidence levels. Recommendations are advisory — they do not bind decisions. Data from different modes is never mixed.

> 🔵 HUMAN ACTION
>
> The Lead Dev allocates developers and the feature issue moves to **Planned**. The kick-off meeting is scheduled.

## Kick-off

Kick-off structure differs by mode. See [2.2 Workflow Modes](2.2-Workflow-Modes) for full mode-specific detail.

### Sprint kick-off (75 minutes)

Sprint assumes the PRD has already passed [prd-completeness-check](1.3-Glossary) (score ≥ 80/100) before kick-off begins.

**Step 1 — Kick-off Dev Review (35 min)**

> 🔵 HUMAN ACTION
>
> The team discusses the PRD on a Teams call (~20 min). The recording is stopped and the team remains on the call.

> 🤖 AGENT ACTION
>
> [kickoff-dev-review](1.3-Glossary) fetches the Teams transcript via Microsoft 365 MCP, reads it alongside the PRD from `.sage/prds/[FEATURE_ID]/prd.md` and Component Specification, and categorises every developer concern into one of seven categories: `PRD_UPDATE`, `PHASE_IMPLICATION`, `CODEBASE_CONFLICT`, `CLARIFICATION_NEEDED`, `ADDRESSED_IN_PRD`, `OUT_OF_SCOPE`, `NO_ACTION`. It asks targeted follow-up questions for unresolved concerns, updates the PRD for confirmed gaps (with team confirmation per change), re-runs [prd-completeness-check](1.3-Glossary) silently, and produces a concern log and phase-splitter briefing note.

> 🔒 ENFORCEMENT POINT
>
> If [prd-completeness-check](1.3-Glossary) drops below threshold after PRD updates, kick-off cannot proceed to Step 2 until the new gap is resolved.

**Step 2 — Phase Breakdown (30 min)**

> 🤖 AGENT ACTION
>
> [phase-splitter](1.3-Glossary) analyses the PRD and codebase. It generates candidate phases, scores each for independence (0–100), builds a dependency map, assigns phase types ([Foundation](1.3-Glossary), [Independent](1.3-Glossary), [Dependent](1.3-Glossary)), estimates effort per phase (2–8 hour target range), and recommends developer profiles. It presents the breakdown document for team adjustment.

> 🔵 HUMAN ACTION
>
> The team reviews and adjusts the phase breakdown. Adjustments are checked for file ownership conflicts, independence score impact, and tier changes. The team confirms the final breakdown.

**Step 3 — Manifest Generation (10 min)**

> 🤖 AGENT ACTION
>
> The [orchestrator](1.3-Glossary) generates the [session manifest](1.3-Glossary) from the confirmed breakdown. It creates Linear phase issues (status: Pending Approval), creates git worktrees at `C:\Sage\worktrees\[FEATURE_ID]\phase-N\` (Sprint only), and writes the session ID to `.sage/sessions/active-session.txt`. The session state is set to `kick-off`.

### Mob kick-off (120 minutes)

Mob kick-off is distinct: [prd-interviewer](1.3-Glossary) runs live with the full team present (co-located or screenshare). A 60-minute feature walkthrough is required the day before.

| Step | Duration | Content |
|---|---|---|
| PRD Discussion | 45 min | Live PRD interview with full team; [prd-interviewer](1.3-Glossary) conducts the interview in real time |
| Phase Breakdown | 45 min | [phase-splitter](1.3-Glossary) generates and team adjusts (same as Sprint Step 2) |
| Session Setup | 30 min | Manifest generation, Linear issues created (no worktrees — Mob uses a single terminal) |

## Phase approval

Phase approval happens in-session during kick-off. After the [phase-splitter](1.3-Glossary) skill generates the phase breakdown, manifest, and Linear issues, it prompts the session driver (PM or Lead Dev) for explicit confirmation. On confirmation, the skill:

1. Updates each Linear phase issue from **Pending Approval** to **Approved** (via Linear MCP)
2. Updates `linearIssueStatus` to `"Approved"` for all phases in the session manifest
3. Sets `sessionState.status` to `"build-sprint"` and `allPhasesApproved` to `true`

The session transitions directly from `kick-off` to `build-sprint` — no separate waiting period is required.

> 🔒 ENFORCEMENT POINT
>
> The [phase-approval-gate](1.3-Glossary) hook blocks S1 (dev-interview) from starting on any phase until that phase's `linearIssueStatus` in the manifest reaches **Approved**. This acts as a safety net if the session was interrupted before approval completed. No agent can bypass this gate.

> **Note:** The `async-approvals` session state remains a valid enum value for edge cases where the approver is not present at kick-off. In standard Sprint and Mob kick-offs, this state is skipped entirely.

## Phase execution (S1–S8)

Each phase progresses through eight steps. In Sprint mode, phases execute in parallel across separate [worktrees](1.3-Glossary). In Mob, Pair, and Solo modes, phases execute sequentially.

### Step sequence

| Step | Name | Agent | Artifact |
|---|---|---|---|
| S1 | [Dev Interview](1.3-Glossary) | [dev-interview](1.3-Glossary) | `phase-{N}-dev-interview-summary.md` |
| S2 | [Implementation Plan](1.3-Glossary) | [implementation-planner](1.3-Glossary) | `phase-{N}-implementation-plan.md` |
| S3 | [Traceability Review](1.3-Glossary) | [traceability-reviewer](1.3-Glossary) | `phase-{N}-traceability-review.md` |
| S4 | [Plan Validation](1.3-Glossary) | [plan-preview-generator](1.3-Glossary) | `phase-{N}-plan-preview.canvas.tsx` / `phase-{N}-plan-preview.md` or `phase-{N}-calculation-proof.md` |
| S5 | [Build](1.3-Glossary) | [test-runner](1.3-Glossary) (TDD), [code-simplifier](1.3-Glossary) | Source files, `phase-{N}-tdd-results.md` |
| S6 | [Code Review](1.3-Glossary) | [code-reviewer](1.3-Glossary) | `phase-{N}-code-review.md` |
| S7 | [Agent Testing](1.3-Glossary) | [test-runner](1.3-Glossary) | `phase-{N}-test-results.md` |
| S8 | [Completion Report](1.3-Glossary) | [orchestrator](1.3-Glossary) | `phase-{N}-completion-report.md` |

### Gates between steps

> 🔒 ENFORCEMENT POINT
>
> The [manifest-step-gate](1.3-Glossary) hook enforces sequential progression. Before any step begins, the hook checks that the prior step's required artifact exists in the phase directory. Steps cannot be skipped, reordered, or combined.

Key gates within the sequence:

| Gate | Blocks | Condition |
|---|---|---|
| [plan-mode-enforcer](1.3-Glossary) | File writes during S1 | S1 runs in Plan mode — all file-write tool calls are blocked |
| [validation-confirmed-gate](1.3-Glossary) | S5 start | Developer must set `validationConfirmed = true` in the manifest |
| [required-references-gate](1.3-Glossary) | S5 start | All files in `requiredReferences` must have been read in the current session |
| [foundation-verified-gate](1.3-Glossary) | S5 for Dependent phases | `foundationVerified = true` in the manifest (set by [orchestrator](1.3-Glossary) after Foundation/Independent phases merge and regression passes) |
| [batch-confirmation-gate](1.3-Glossary) | Next batch in Checkpoint mode | Developer must set `batches[N].confirmed = true` |
| [tdd-results-gate](1.3-Glossary) | S6 start | `phase-{N}-tdd-results.md` must exist with `STATUS: PASS` |
| [code-review-gate](1.3-Glossary) | S7 start | `phase-{N}-code-review.md` must contain `Critical findings: 0` |
| [completion-report-stop-gate](1.3-Glossary) | Agent turn end at S8 | `phase-{N}-test-results.md` must contain `STATUS: PASS` |

### Build mode within S5

> 🔵 HUMAN ACTION
>
> During S1, the developer chooses between [Autonomous](1.3-Glossary) and [Checkpoint](1.3-Glossary) build mode. This choice is available in all four workflow modes.

- **Autonomous**: the agent builds all tasks in sequence. The developer reviews at S6.
- **Checkpoint**: the [implementation-planner](1.3-Glossary) generates batch definitions (written to the manifest). After each batch, the agent produces a batch review document. The developer reviews and sets `batches[N].confirmed = true` before the next batch begins.

### Phase types and parallelism (Sprint mode)

| Phase type | Parallel start | S5 gate | Merge order |
|---|---|---|---|
| [Foundation](1.3-Glossary) | Starts immediately | No extra gate | Merges first |
| [Independent](1.3-Glossary) | Starts immediately | No extra gate | Merges after Foundation |
| [Dependent](1.3-Glossary) | S1–S4 run in parallel | S5 blocked until `foundationVerified = true` | Merges last |

> 🤖 AGENT ACTION
>
> In Sprint mode, [sprint-coordinator](1.3-Glossary) monitors all phase lanes in real time. It reads the session manifest and per-lane telemetry to surface lane status, bottlenecks, and merge sequencing on demand. It never takes action — it observes and reports only. Sprint-coordinator is exclusive to Sprint mode; other modes do not use it.

## Review and merge

When all phases reach Build Complete, the session state moves to `review-merge`.

> 🤖 AGENT ACTION
>
> The [orchestrator](1.3-Glossary) coordinates the merge sequence:
> 1. Foundation phases merge first (they have downstream consumers)
> 2. Independent phases merge next
> 3. The orchestrator sets `foundationVerified = true` in the manifest after Foundation and Independent phases are merged and regression passes
> 4. Dependent phases merge last

> 🤖 AGENT ACTION
>
> The [gap-analyzer](1.3-Glossary) analyses the merged implementation against the PRD and test results. It identifies unimplemented acceptance criteria, test coverage holes, and any gaps. It produces `gap-analysis-[feature-id].md`. It does not fix gaps — it reports only.

> 🤖 AGENT ACTION
>
> The [orchestrator](1.3-Glossary) triggers post-merge regression testing across all phase scoped files. If regression fails, the orchestrator reports which phases are affected and blocks feature closure.

> 🤖 AGENT ACTION
>
> The [feature-doc-generator](1.3-Glossary) generates end-user and technical documentation for the completed feature and writes it to `.sage/prds/[FEATURE_ID]/feature-docs/` as two files: `technical-wiki.md` and `user-guide.md`. Documentation reflects what was built, not what was planned.

> 🔵 HUMAN ACTION
>
> The Lead Dev reviews the gap analysis, regression results, and documentation. Feature closure is confirmed.

## Post-cycle

After feature closure, the session state moves to `complete`.

Three subsystems run after every completed work cycle:

### Session performance evaluation (every cycle)

> 🤖 AGENT ACTION
>
> [session-performance-evaluator](1.3-Glossary) reads `workflow-telemetry.jsonl` and phase artifacts. It scores execution across five dimensions: step compliance, hook discipline, TDD cycle quality, gate bypass attempts, and phase duration. Systematic violations (same hook rejection 3+ times, any gate bypass attempt, same fail pattern across consecutive cycles) generate Linear issues with label `violation` for the Lead Dev.

### Skill effectiveness evaluation (every 5 cycles)

> 🤖 AGENT ACTION
>
> [skill-effectiveness-evaluator](1.3-Glossary) analyses execution patterns across the full telemetry dataset. When a skill shows consistent underperformance, it proposes a targeted diff to the skill's SKILL.md, stages it to `.skill-update-staging/`, and creates a Linear issue with label `skill-update` and status Pending Approval. Approvers: Product Manager for [prd-completeness-check](1.3-Glossary) and [prd-interviewer](1.3-Glossary); Lead Dev for [phase-splitter](1.3-Glossary) and all others. The evaluator cannot apply its own diffs. It suppresses re-proposals for 2 cycles after a rejection.

### Metrics recording (every cycle)

> 🤖 AGENT ACTION
>
> [intel-recorder](1.3-Glossary) records delivery metrics to `.sage/intel/velocity-history.jsonl` and optionally publishes to the Notion metrics dashboard. Metrics captured per phase include: estimated vs actual hours, build mode, step durations (S1–S7), hook rejection count, TDD GREEN first-pass rate, REFACTOR completion rate, S7 test pass rate, critical findings at S6, and foundation wait time (Dependent phases only). Datasets are maintained separately per workflow mode — Sprint data is never mixed with Mob, Pair, or Solo data.

## Session manifest location

The session manifest lives at:
`.sage/sessions/[session-id]/session-manifest.md`

The active session ID is stored in:
`.sage/sessions/active-session.txt`

Phase artifacts are written to:
`.sage/sessions/[session-id]/phase-[N]/`

All tool calls are logged automatically by the [telemetry-logger](1.3-Glossary) hook to `workflow-telemetry.jsonl` in the session directory.
