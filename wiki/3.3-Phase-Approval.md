# 3.3 Phase Approval and Build Sprint Launch

*This page covers how phase issues move from Pending Approval to Approved during kick-off and how developers know when to start — and serves the Product Manager, Lead Dev, and Developers.*

| Step | Actor | Action | Result |
|------|-------|--------|--------|
| 1. Phase issues created | Agent (phase-splitter) | Linear issues at Pending Approval | Phases visible in Linear |
| 2. Review phase breakdown | PM or Lead Dev (session driver) | Review breakdown during kick-off, request adjustments | Understanding and agreement on each phase |
| 3. Confirm approval in session | PM or Lead Dev (session driver) | Respond "yes" to phase-splitter approval prompt | Agent updates Linear + manifest |
| 4. Developer opens worktree | Developer | Open worktree in Cursor (Sprint) or start in repo (Mob/Pair) | S1 begins |

---

## Context

During [Sprint Kick-off](3.2-Sprint-Kickoff) or Mob Kick-off, the [phase-splitter](1.3-Glossary) skill generates the phase breakdown, creates Linear issues at **Pending Approval**, and then immediately prompts the session driver for approval confirmation. Approval happens in the same session — there is no separate async waiting period.

No build work can begin until the phase is approved. This is enforced structurally by a hook.

---

## How Approval Works

The phase-splitter skill (Step 11) handles approval:

1. After generating all session artifacts (manifest, Linear issues, worktrees), the skill presents a summary of all phases
2. It asks the session driver: "Do you approve all phases to proceed to the build sprint?"
3. On explicit confirmation:
   - Linear phase issues are moved from **Pending Approval** to **Approved** (via Linear MCP)
   - `linearIssueStatus` is updated to `"Approved"` in each phase's manifest runtime block
   - `sessionState.status` moves to `"build-sprint"` and `allPhasesApproved` is set to `true`

If the session driver declines or requests changes, the skill returns to facilitation (Step 9) for further adjustment.

**Approval criteria** — the session driver confirms that:
- Each phase objective is correct and complete
- The scoped files are accurate
- The effort estimates are reasonable
- Dependencies are correctly mapped
- The developer profile recommendations make sense

---

## The phase-approval-gate Hook

> 🔒 **ENFORCEMENT POINT**  
> The `phase-approval-gate` hook structurally blocks S1 ([dev-interview](1.3-Glossary)) from starting until the phase's `linearIssueStatus` in the manifest is in the approved set. This acts as a safety net for interrupted sessions.

**Hook details:**

| Property | Value |
|----------|-------|
| Hook ID | `phase-approval-gate` |
| Event | `preToolUse` |
| Blocking | Yes |
| Script | `hooks/scripts/phase_approval_gate.py` |
| Timeout | 3000ms |

**Approved status set:**

The hook permits tool calls when `linearIssueStatus` matches any of:

- `Approved`
- `Foundation Verified`
- `In Progress`
- `Build Complete`
- `Done`

**Behaviour:**

1. The hook reads the session manifest's `runtime.currentStep` for the phase
2. If `currentStep` is not `dev-interview`, the hook permits (it only gates S1 entry)
3. If `currentStep` is `dev-interview`, it reads `runtime.linearIssueStatus`
4. If the status is not in the approved set, the hook **blocks** and emits a `hook_rejection` telemetry event
5. The rejection message tells the developer to ensure approval has been completed

**Fires once:** After S1 completes and the step advances past `dev-interview`, the hook no longer checks approval status. It does not re-gate on subsequent steps.

---

## Manifest Update

The `linearIssueStatus` field in the session manifest is updated by the phase-splitter skill at kick-off confirmation time. The hook reads from the manifest, not directly from Linear. The manifest is the source of truth for gate decisions.

If a session was interrupted before Step 11 completed (e.g. kick-off ended early), the manifest may still show `Pending Approval`. In that case, the developer must manually update the manifest field to `"Approved"` after confirming the Linear issues are at the correct status.

---

## How Developers Know When to Start

Developers learn their phase is approved through:

1. **Kick-off conclusion** — if present at kick-off, they witness the approval confirmation
2. **Linear notification** — the status change to Approved triggers a Linear notification to the assigned developer
3. **Checking the manifest** — reading `.sage/sessions/[session-id]/session-manifest.md` and checking their phase's `linearIssueStatus`
4. **Attempting to start** — if a developer opens their worktree and invokes the dev-interview agent, the phase-approval-gate hook will either permit (approved) or block with a clear message (not yet approved)

---

## Starting Build Work

Once approved, the developer proceeds:

**Sprint mode:**
1. Open the phase worktree in Cursor: `C:\Sage\worktrees\[FEATURE_ID]\phase-[N]\`
2. The worktree is on branch `LIN-[phase-issue-id]-phase-[N]-[kebab-objective]`
3. Invoke the [dev-interview](1.3-Glossary) agent to begin S1

**Mob mode:**
1. The team works in the same repository on the same terminal
2. The [orchestrator](1.3-Glossary) opens Phase Chats at phase transitions
3. Invoke the dev-interview agent to begin S1

**Pair mode:**
1. Developers work sequentially in the same repository (no worktrees)
2. Each developer begins their assigned phase after approval

---

## Phase Issue Status Lifecycle

The full Linear status progression for phase issues in Sprint mode:

```
Pending Approval → Approved → In Progress → Build Complete → Done
                           ↘ Foundation Verified (for Dependent phases after regression passes)
```

| Status | Meaning |
|--------|---------|
| Pending Approval | Created at kick-off, awaiting PM + Lead Dev review |
| Approved | Reviewed and approved — developer can begin S1 |
| Foundation Verified | Dependent phase — upstream Foundation has merged and regression passed |
| In Progress | Developer is actively working (S1–S7) |
| Build Complete | All steps S1–S8 complete, PR ready for review |
| Done | Merged to main |
