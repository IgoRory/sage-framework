# 3.3 Phase Approval and Build Sprint Launch

*This page covers the approval gate between kick-off and build work — how phase issues move from Pending Approval to Approved and how developers know when to start — and serves the Product Manager, Lead Dev, and Developers.*

| Step | Actor | Action | Result |
|------|-------|--------|--------|
| 1. Phase issues created | Agent (phase-splitter) | Linear issues at Pending Approval | Phases visible in Linear |
| 2. Review phase scope | PM + Lead Dev | Read manifest, review scoped files and objectives | Understanding of each phase |
| 3. Approve in Linear | PM + Lead Dev | Set Linear issue status → Approved | Gate unlocked for that phase |
| 4. Developer opens worktree | Developer | Open worktree in Cursor (Sprint) or start in repo (Mob/Pair) | S1 begins |

---

## Context

After [Sprint Kick-off](3.2-Sprint-Kickoff) or Mob Kick-off completes, every phase exists as a Linear issue at status **Pending Approval**. The [session manifest](1.3-Glossary) records each phase's `linearIssueStatus` field as `Pending Approval`.

No build work can begin until the phase is approved. This is enforced structurally by a hook.

---

## Who Approves

> 🔵 **HUMAN ACTION**  
> Both the **Product Manager** and **Lead Dev** review and approve each phase issue in Linear. Approval means:
> - The phase objective is correct and complete
> - The scoped files are accurate
> - The effort estimate is reasonable
> - Dependencies are correctly mapped
> - The developer profile recommendation makes sense for the assigned developer

Approval is performed by setting the Linear issue status from **Pending Approval** to **Approved**.

---

## The phase-approval-gate Hook

> 🔒 **ENFORCEMENT POINT**  
> The `phase-approval-gate` hook structurally blocks S1 ([dev-interview](1.3-Glossary)) from starting until the phase's Linear issue status is in the approved set.

**Hook details:**

| Property | Value |
|----------|-------|
| Hook ID | `phase-approval-gate` |
| Event | `preToolUse` |
| Blocking | Yes |
| Script | `.cursor/hooks/scripts/phase_approval_gate.py` |
| Timeout | 3000ms |

**Approved status set:**

The hook permits tool calls when `linearIssueStatus` matches any of:

- `Approved`
- `Foundation Verified`
- `In Progress`
- `Build Complete`
- `Done`

**Behaviour:**

1. The hook reads the session manifest's `runtime.currentStep` for the phase
2. If `currentStep` is not `dev-interview`, the hook permits (it only gates S1 entry)
3. If `currentStep` is `dev-interview`, it reads `runtime.linearIssueStatus`
4. If the status is not in the approved set, the hook **blocks** and emits a `hook_rejection` telemetry event
5. The rejection message tells the developer: "The Product Manager and Lead Dev must approve this phase issue in Linear before build work can begin."

**Fires once:** After S1 completes and the step advances past `dev-interview`, the hook no longer checks approval status. It does not re-gate on subsequent steps.

---

## Updating the Manifest

When the PM or Lead Dev approves a phase in Linear, the `linearIssueStatus` field in the session manifest must be updated to reflect the new status. This update is performed by:

- The developer manually editing the manifest, or
- The [orchestrator](1.3-Glossary) agent detecting the Linear status change (when running)

The hook reads from the manifest, not directly from Linear. The manifest is the source of truth for gate decisions.

---

## How Developers Know When to Start

Developers learn their phase is approved through:

1. **Linear notification** — the status change to Approved triggers a Linear notification to the assigned developer
2. **Checking the manifest** — reading `.sage/sessions/[session-id]/session-manifest.md` and checking their phase's `linearIssueStatus`
3. **Attempting to start** — if a developer opens their worktree and invokes the dev-interview agent, the phase-approval-gate hook will either permit (approved) or block with a clear message (not yet approved)

---

## Starting Build Work

Once approved, the developer proceeds:

**Sprint mode:**
1. Open the phase worktree in Cursor: `C:\Sage\worktrees\[FEATURE_ID]\phase-[N]\`
2. The worktree is on branch `LIN-[phase-issue-id]-phase-[N]-[kebab-objective]`
3. Invoke the [dev-interview](1.3-Glossary) agent to begin S1

**Mob mode:**
1. The team works in the same repository on the same terminal
2. The [orchestrator](1.3-Glossary) opens Phase Chats at phase transitions
3. Invoke the dev-interview agent to begin S1

**Pair mode:**
1. Developers work sequentially in the same repository (no worktrees)
2. Each developer begins their assigned phase after approval

---

## Phase Issue Status Lifecycle

The full Linear status progression for phase issues in Sprint mode:

```
Pending Approval → Approved → In Progress → Build Complete → Done
                           ↘ Foundation Verified (for Dependent phases after regression passes)
```

| Status | Meaning |
|--------|---------|
| Pending Approval | Created at kick-off, awaiting PM + Lead Dev review |
| Approved | Reviewed and approved — developer can begin S1 |
| Foundation Verified | Dependent phase — upstream Foundation has merged and regression passed |
| In Progress | Developer is actively working (S1–S7) |
| Build Complete | All steps S1–S8 complete, PR ready for review |
| Done | Merged to main |
