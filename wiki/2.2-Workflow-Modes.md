# 2.2 Workflow Modes

*Describes the four SAGE workflow modes — mob, sprint, pair, and solo — their configuration, constraints, and selection criteria, for Lead Devs and Product Managers choosing how to deliver a feature.*

| Property | Mob | Sprint | Pair | Solo |
|---|---|---|---|---|
| Description | Single terminal, sequential, co-located or screenshare | Parallel worktrees, distributed team, async-first | Sequential phases, 2 devs, async kick-off | Single developer, hotfix or minor work |
| Developers | 1–6 | 2–3 | 2 | 1 |
| Worktrees | No | Yes (`C:\Sage\worktrees\`) | No | No |
| Phase execution | Sequential | Parallel | Sequential | Sequential |
| Kick-off | Required (mob-kickoff, 120 min) | Required (sprint-kickoff, 75 min) | Required (async) | Not required |
| Feature walkthrough | Required (day before, 60 min) | Not required | Not required | Not required |
| PRD required | Yes | Yes | Yes | No |
| [Sprint-coordinator](1.3-Glossary) | No | Yes | No | No |
| Foundation Verified state | No | Yes | No | No |
| S1–S8 step sequence | Enforced | Enforced | Enforced | Enforced |
| [Build mode](1.3-Glossary) choice | Autonomous / Checkpoint | Autonomous / Checkpoint | Autonomous / Checkpoint | Autonomous / Checkpoint |

## Sprint

Sprint is the primary [workflow mode](1.3-Glossary) for feature delivery. It uses parallel [worktrees](1.3-Glossary), an async-first cadence, and a distributed team of 2–3 developers.

### Configuration

| Property | Value |
|---|---|
| `modes.sprint.description` | Parallel worktrees, distributed team, async-first |
| `modes.sprint.minDevs` | 2 |
| `modes.sprint.maxDevs` | 3 |
| `modes.sprint.worktrees` | `true` |
| `modes.sprint.worktreeRoot` | `C:\Sage\worktrees\` |
| `modes.sprint.prdRequired` | `true` |

### Prerequisites

The PRD must have passed [prd-completeness-check](1.3-Glossary) with a score ≥ 80/100 before Sprint kick-off begins. The feature issue must be in the **Ready** or **Planned** state.

### Kick-off (sprint-kickoff, 75 minutes)

| Step | Duration | Skill / agent | What happens |
|---|---|---|---|
| Kick-off Dev Review | 35 min | [kickoff-dev-review](1.3-Glossary) | Team discusses PRD on Teams; transcript processed; concerns categorised; PRD updated for confirmed gaps; completeness re-checked |
| Phase Breakdown | 30 min | [phase-splitter](1.3-Glossary) | Candidate phases generated, scored for independence, dependency map built, team adjusts and confirms |
| Manifest Generation | 10 min | [orchestrator](1.3-Glossary) | [Session manifest](1.3-Glossary) written, Linear phase issues created (Pending Approval), git worktrees created at `C:\Sage\worktrees\[feature-id]\phase-N\` |

### Phase execution

Phases execute in parallel across separate worktrees. Each phase progresses through the full S1–S8 [step sequence](1.3-Glossary):

1. **S1** — Dev Interview
2. **S2** — Implementation Plan
3. **S3** — Traceability Review
4. **S4** — Plan Validation
5. **S5** — Build
6. **S6** — Code Review
7. **S7** — Agent Testing
8. **S8** — Completion Report

> 🔒 ENFORCEMENT POINT
>
> All eight steps are enforced in order by the [manifest-step-gate](1.3-Glossary) hook. No step can be skipped, reordered, or combined, regardless of workflow mode.

### Phase types

Sprint uses three [phase types](1.3-Glossary) assigned by [phase-splitter](1.3-Glossary):

- **[Foundation](1.3-Glossary)**: No upstream dependencies. Has downstream consumers. Starts immediately. Merges first.
- **[Independent](1.3-Glossary)**: No upstream or downstream dependencies. Starts immediately. Merges after Foundation.
- **[Dependent](1.3-Glossary)**: Has upstream dependencies. S1–S4 execute in parallel with other phases. S5 (Build) is blocked by the [foundation-verified-gate](1.3-Glossary) until `foundationVerified = true` in the manifest.

> 🔒 ENFORCEMENT POINT
>
> The [foundation-verified-gate](1.3-Glossary) hook blocks Dependent phase lanes from entering S5 until the [orchestrator](1.3-Glossary) sets `foundationVerified = true` after all Foundation and Independent phases have merged and regression has passed.

### Sprint-specific features

**[Sprint-coordinator](1.3-Glossary)**: A background, read-only agent active during the Build phase (S5). It monitors all phase lanes in real time, reads the session manifest and per-lane telemetry, and surfaces lane status, bottlenecks, and merge sequencing on demand. It never takes action and never writes to any file. Sprint-coordinator exists only in Sprint mode.

**Foundation Verified phase issue state**: Sprint phase issues include a sixth state — **Foundation Verified** — between Approved and In Progress. This state applies to Dependent phases after Foundation phases merge and regression passes. Mob, Pair, and Solo phase issues do not include this state.

### Linear phase issue states (Sprint)

**Pending Approval** → **Approved** → **Foundation Verified** → **In Progress** → **Build Complete** → **Done**

## Mob

Mob mode uses a single terminal with sequential phase execution. The team is co-located or connected via screenshare. 1–6 developers participate.

### Configuration

| Property | Value |
|---|---|
| `modes.mob.description` | Single terminal, sequential, co-located or screenshare |
| `modes.mob.minDevs` | 1 |
| `modes.mob.maxDevs` | 6 |
| `modes.mob.worktrees` | `false` |
| `modes.mob.prdRequired` | `true` |

### Prerequisites

A 60-minute feature walkthrough is required the day before the kick-off session.

### Kick-off (mob-kickoff, 120 minutes)

Mob kick-off is distinct from Sprint kick-off: [prd-interviewer](1.3-Glossary) runs live with the full team present in the same room (or on screenshare). The PRD is created during kick-off, not beforehand.

| Step | Duration | Skill / agent | What happens |
|---|---|---|---|
| PRD Discussion | 45 min | [prd-interviewer](1.3-Glossary) | Live PRD interview conducted with the full team present; questions asked one at a time; codebase reconnaissance performed beforehand; PRD draft and Component Specification generated on approval |
| Phase Breakdown | 45 min | [phase-splitter](1.3-Glossary) | Same process as Sprint — candidate phases generated, scored, dependency map built, team adjusts and confirms |
| Session Setup | 30 min | [orchestrator](1.3-Glossary) | Session manifest written, Linear phase issues created; no worktrees (single terminal) |

> 🔵 HUMAN ACTION
>
> After the live PRD interview (and before Phase Breakdown), the PM runs [prd-completeness-check](1.3-Glossary) against the generated PRD. The score must reach threshold before proceeding.

### Phase execution

Phases execute sequentially through a single terminal. The [orchestrator](1.3-Glossary) automatically opens Phase Chats at phase transitions and manages progression via gates. Each phase follows the same S1–S8 step sequence enforced by hooks.

### Phase types

Mob mode assigns the same three phase types (Foundation, Independent, Dependent), but phases execute sequentially. The [foundation-verified-gate](1.3-Glossary) still applies to Dependent phases — the gate checks `foundationVerified` in the manifest regardless of mode.

### Linear phase issue states (Mob)

**Pending Approval** → **Approved** → **In Progress** → **Build Complete** → **Done**

No Foundation Verified state.

## Pair

Pair mode supports two developers working sequential phases with an async kick-off.

### Configuration

| Property | Value |
|---|---|
| `modes.pair.description` | Sequential phases, 2 devs, async kick-off |
| `modes.pair.minDevs` | 2 |
| `modes.pair.maxDevs` | 2 |
| `modes.pair.worktrees` | `false` |
| `modes.pair.prdRequired` | `true` |

### How it differs from Sprint

- **No worktrees**: phases execute sequentially, not in parallel.
- **Async kick-off**: kick-off runs asynchronously rather than as a scheduled meeting.
- **No sprint-coordinator**: there is no background lane monitor.
- **No Foundation Verified state**: Pair uses the 5-state phase issue machine (Pending Approval → Approved → In Progress → Build Complete → Done).
- **Same S1–S8 enforcement**: all hooks apply identically. Build mode (Autonomous / Checkpoint) is available.

### Linear phase issue states (Pair)

**Pending Approval** → **Approved** → **In Progress** → **Build Complete** → **Done**

> Procedural detail for Pair mode will be added when Pair mode is activated. The configuration above is current and enforced.

## Solo

Solo mode is for a single developer handling hotfixes or minor work. It has the lightest ceremony of any mode.

### Configuration

| Property | Value |
|---|---|
| `modes.solo.description` | Single developer, hotfix or minor work |
| `modes.solo.minDevs` | 1 |
| `modes.solo.maxDevs` | 1 |
| `modes.solo.worktrees` | `false` |
| `modes.solo.kickoff.required` | `false` |
| `modes.solo.prdRequired` | `false` |

### How it differs from other modes

- **No PRD required**: Solo does not require a PRD. It is the only mode where `prdRequired = false`.
- **No kick-off**: Solo skips the kick-off session entirely. The session manifest is created directly.
- **S1 exception**: S1 (Dev Interview) is not required in Solo mode. Absence of `phase-{N}-dev-interview-summary.md` is not a step compliance failure for Solo.
- **Same S2–S8 enforcement**: all other hooks apply identically. Steps S2–S8 execute in order.
- **Build mode available**: Autonomous and Checkpoint are both available.

### Linear phase issue states (Solo)

**Pending Approval** → **Approved** → **In Progress** → **Build Complete** → **Done**

## Choosing a mode

Use this decision sequence to select a mode:

**1. Is this a hotfix or minor change with no PRD?**
→ **Solo**. One developer, no kick-off, no PRD. S1 (Dev Interview) is optional.

**2. Is the team co-located (or willing to screenshare for the full build) and does the feature benefit from real-time collaboration on the PRD?**
→ **Mob**. The live PRD interview with the full team produces the richest PRD context. Requires a 60-minute feature walkthrough the day before and a 120-minute kick-off. Supports 1–6 developers. Sequential execution — no parallelism.

**3. Are exactly 2 developers available and the feature is small enough for sequential phases?**
→ **Pair**. Async kick-off reduces scheduling overhead. Sequential execution. No worktrees. Procedural detail is pending activation.

**4. Are 2–3 developers available, the feature has multiple independent phases, and the team works async?**
→ **Sprint**. Parallel worktrees, distributed team, async-first. Requires a completed PRD (score ≥ 80/100) before kick-off. 75-minute kick-off. Full phase type system (Foundation / Independent / Dependent). Sprint-coordinator monitors all lanes. This is the default mode for standard feature delivery.

### Decision factors

| Factor | Favours |
|---|---|
| PRD does not exist yet and team wants to write it live | Mob |
| Team is distributed across time zones | Sprint |
| Feature has 3+ parallelisable phases | Sprint |
| Feature is small with 1–2 phases | Pair or Solo |
| No PRD needed (hotfix, config change) | Solo |
| Team wants real-time, high-bandwidth collaboration | Mob |
| Scheduling a synchronous kick-off is difficult | Pair (async kick-off) |

## What all modes share

Regardless of mode, every SAGE session enforces:

- **S1–S8 [step sequence](1.3-Glossary)**: the [manifest-step-gate](1.3-Glossary) hook enforces sequential step progression in all modes
- **[Build mode](1.3-Glossary) choice**: Autonomous and Checkpoint are available in all four modes; the developer chooses during S1
- **[Validation-confirmed gate](1.3-Glossary)**: S5 is blocked until the developer sets `validationConfirmed = true` in all modes
- **[Hook enforcement](1.3-Glossary)**: all hooks fire in all modes — [telemetry-logger](1.3-Glossary), [plan-mode-enforcer](1.3-Glossary), [manifest-step-gate](1.3-Glossary), [phase-approval-gate](1.3-Glossary), [required-references-gate](1.3-Glossary), [tdd-results-gate](1.3-Glossary), [code-review-gate](1.3-Glossary), [completion-report-stop-gate](1.3-Glossary)
- **[Telemetry](1.3-Glossary)**: all tool calls are logged to `workflow-telemetry.jsonl` by the [telemetry-logger](1.3-Glossary) hook
- **Post-cycle evaluation**: [session-performance-evaluator](1.3-Glossary) runs after every cycle; [skill-effectiveness-evaluator](1.3-Glossary) runs every 5 cycles; [intel-recorder](1.3-Glossary) records metrics per mode
- **Linear issue tracking**: feature issues follow the same state machine (Backlog → PRD In Progress → PRD Under Review → Ready → Planned) in all modes
