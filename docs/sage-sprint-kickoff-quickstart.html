Before Kick-off — Confirm These Are Done

  • PRD exists at .sage/prds/[FEATURE_ID]/prd.md and has passed prd-completeness-check with score ≥ 80/100
  • Component specification exists at .sage/prds/[FEATURE_ID]/component-spec.md (UI features)
  • Linear feature issue is at status Ready or Planned
  • All team members have read the PRD before the call
  • Cursor IDE is open with the Profitability repo workspace
  • Microsoft Teams is ready to start a recorded call
Step 1 — Kick-off Dev Review · 35 min
1
Start the Teams Call
~1 min
You do this

Open Microsoft Teams. Start a recorded meeting with the full team (2–3 developers + PM + Lead Dev).

Confirm recording has started before moving on.

2
Discuss the PRD on the Call
~20 min
You do this — whole team participates

Walk through the PRD together. Developers raise concerns, flag ambiguities, highlight areas where the PRD conflicts with what they know about the codebase. PM clarifies intent.

There is no agent involved at this point. This is a normal team conversation captured by the Teams recording.

3
Stop the Recording
~1 min
You do this

Stop the Teams recording. Do not hang up — the team stays on the call. You’ll need them for follow-up questions in a few minutes.

Copy the Teams meeting link. You will provide this to the agent next.

4
Invoke kickoff-dev-review
~3 min (agent processing)
You type this in Cursor chat

Open Cursor. In the chat panel, type:

Prompt Run the kickoff-dev-review skill for [FEATURE_ID]. Teams meeting link: [paste link]
kickoff-dev-review skill runs — wait and watch

The skill fetches the transcript from the Teams meeting via the Microsoft 365 MCP. It then reads the PRD at .sage/prds/[FEATURE_ID]/prd.md and the component specification at .sage/prds/[FEATURE_ID]/component-spec.md.

It processes every developer concern from the transcript and categorises each into one of seven types:

Concern categories
  • PRD_UPDATE — gap in the PRD that must be fixed
  • PHASE_IMPLICATION — affects how phases should be split
  • CODEBASE_CONFLICT — contradiction with existing code (highest priority)
  • CLARIFICATION_NEEDED — ambiguous, needs follow-up
  • ADDRESSED_IN_PRD — PRD already covers this
  • OUT_OF_SCOPE — valid but outside feature boundary
  • NO_ACTION — resolved in discussion

If the transcript is not yet available (still processing), the skill will pause and tell you. Wait for Teams to finish processing.

5
Answer Follow-up Questions
~10 min
You + team answer in real time

The agent presents follow-up questions for concerns categorised as CLARIFICATION_NEEDED and CODEBASE_CONFLICT. One question per concern, one at a time.

Answer in Cursor chat. Relay answers from the team who are still on the Teams call. The agent re-categorises each concern based on your answer.

6
Confirm PRD Updates
~5 min
kickoff-dev-review proposes updates

For each confirmed PRD_UPDATE concern, the agent drafts a specific change to the PRD and presents it for your confirmation. Updates are presented one at a time, not batched.

You confirm each update

Review each proposed PRD change. Approve or reject individually. Only approved changes are applied to .sage/prds/[FEATURE_ID]/prd.md.

7
Completeness Re-check
~1 min (automated)
prd-completeness-check runs silently

After all PRD updates are applied, kickoff-dev-review automatically re-runs prd-completeness-check against the updated PRD. This happens without you typing anything.

Completeness gate

Score must remain ≥ 80/100. If PRD updates introduced a new gap that drops the score, the agent surfaces the finding immediately. You must resolve it before moving to phase breakdown. The phase-splitter will not run against a below-threshold PRD.

Outputs from Dev Review
  • [SESSION_ROOT]/kickoff-dev-review-log.md — all concerns with categories and resolutions
  • [SESSION_ROOT]/phase-splitter-briefing.md — phase implications, codebase conflicts, PRD updates, updated completeness score
Step 2 — Phase Breakdown · 30 min
8
Invoke phase-splitter
~5 min (agent processing)
You type this in Cursor chat
Prompt Run the phase-splitter skill for [FEATURE_ID]
phase-splitter skill runs — wait and watch

The skill reads the PRD, component spec, and the phase-splitter briefing produced in Step 7. It then scans the codebase to identify every file this feature will touch.

It generates candidate phases by applying splitting heuristics. Each phase must have:

Phase requirements
  • Single objective — one verb phrase describes the entire phase
  • Exclusive file ownership — no file appears in two phases
  • At least one independently runnable test
  • Effort in the 2–8 hour range

Each phase is scored for independence (0–100). Phases below 60 are flagged. A dependency map is built and each phase is assigned a type:

Phase types
  • Foundation — no upstream deps, has downstream consumers. Merges first.
  • Independent — no upstream or downstream deps. Starts in parallel with Foundation.
  • Dependent — has upstream deps. S1–S4 run in parallel; S5 build is blocked until Foundation is verified.
9
Review Phase Breakdown with Team
~15 min
phase-splitter presents the breakdown

The agent walks through the proposed phases one by one:

  • Phase count and overall structure
  • Tier structure (Foundation / Independent / Dependent)
  • Independence flags for any phase scoring below 60
  • Effort ranges per phase (low–high hours)
  • Developer profile recommendations (UI-heavy, Backend-heavy, Database, Full-stack, Any)
Team discusses adjustments

Propose any changes — merging phases, splitting further, reassigning types. For each proposed adjustment, the agent checks for file ownership conflicts, independence score impact, and tier impact.

Developer profiles only — no named developers are assigned at this point. Assignment happens during the planning cycle.

10
Confirm the Breakdown
~2 min
You confirm

When the team is satisfied, confirm the breakdown in chat. The agent will not finalise until you explicitly confirm.

Prompt Confirmed. Finalise the phase breakdown.
Path validation gate

All scopedFiles and requiredReferences in the manifest are validated against the codebase. Files must resolve to EXISTS or NEW (to be created). Any path resolving to MISSING blocks manifest finalisation until you correct or declare it NEW.

Output
  • [SESSION_ROOT]/phase-breakdown.md — final agreed phases with scores, types, effort, and profiles
Step 3 — Manifest Generation · 10 min
11
Session Manifest, Linear Issues, and Worktrees
~10 min (automated)
phase-splitter + orchestrator — fully automated

Once you confirmed in Step 10, the following happens automatically. You are watching, not acting.

1. Session manifest created
  • Written to .sage/sessions/[session-id]/session-manifest.md
  • Session ID = Linear feature issue ID (e.g. PROF-7)
  • Active session pointer written to .sage/sessions/active-session.txt
  • Each phase starts at: currentStep: "dev-interview", buildMode: "autonomous", validationConfirmed: false, all step statuses: "pending"
2. Linear phase issues created (via Linear MCP)
  • One issue per phase
  • Title format: [Feature title] -- Phase N: [objective]
  • Status: Pending Approval
  • Upstream dependencies linked between phase issues
  • Mode label applied: mode:sprint
3. Git worktrees created (Sprint mode only)
  • One worktree per phase at C:\Sage\worktrees\[FEATURE_ID]\phase-[N]\
  • Branch naming: LIN-[phase-issue-id]-phase-[N]-[kebab-objective]
4. TDD specifications generated
  • One TDD spec per phase written to [SESSION_ROOT]/phase-[N]/phase-[N]-tdd-spec.md
  • Every scenario mapped from PRD acceptance criteria in Given/When/Then format
  • Generated by the orchestrator agent
After kick-off — Phase Approval
12
Approve Phases in Linear
Async — PM + Lead Dev
PM + Lead Dev do this in Linear

Every phase issue is now at Pending Approval in Linear. Both the Product Manager and Lead Dev review each phase’s scope, scoped files, effort estimate, and dependency mapping.

When satisfied, set each phase issue status from Pending Approval → Approved in Linear.

phase-approval-gate — enforced by hook

The phase-approval-gate hook blocks the dev-interview agent (S1) from starting on any phase until that phase’s Linear issue status is Approved.

Hook ID: phase-approval-gate
Event: preToolUse
Script: .cursor/hooks/scripts/phase_approval_gate.py

If a developer tries to invoke the dev-interview before approval, the hook blocks with: “The Product Manager and Lead Dev must approve this phase issue in Linear before build work can begin.”

After approval — developers begin S1

Each developer opens their phase worktree in Cursor and invokes the dev-interview agent. During S1, the developer will choose a build mode:

Autonomous
The agent builds the full phase in one continuous pass. Fewer interruptions. You review at the end. This is the default mode.
Checkpoint
The build is divided into batches. After each batch, the agent pauses and writes a review document. You must confirm each batch before the next can start. More oversight, more frequent review points.
