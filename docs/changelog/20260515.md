# Changelog - 2026-05-15

## Align SAGE Agents With Company Skill Guidance

### Rationale

The SAGE agent prompts were reconciled with guidance from the company Mob session skills so the framework can benefit from stronger discovery, traceability, review, and documentation practices without disturbing SAGE's artifact-driven gates.

The main intent was to import useful depth where the company skills were clearly applicable, while avoiding risky direct delegation to Mob-specific flows that depend on live team pauses, different artifact paths, or repo-specific assumptions.

### Changes

- Added spec gap analysis, feature exploration, delta analysis, and reuse checks to the S1 developer interview flow.
- Expanded traceability review to include codebase context, PRD quality checks, discrepancy categories, and the full PRD to TDD spec to implementation plan chain.
- Adapted company code review guidance into SAGE review passes without requiring unavailable PR-history agents or ADO/GitHub metadata.
- Added optional HTML validation mockup guidance to S4 while keeping Canvas, Markdown, and calculation proof artifacts as the SAGE source of truth.
- Expanded feature documentation guidance using company wiki/user-guide depth while preserving the SAGE requirement to generate separate `technical-wiki.md` and `user-guide.md` files.
- Generalized hardcoded Profitability domain references so agents verify current contracts from the PRD, manifest references, and scoped code/schema before using specific object, measure, status, or flag names.

### Regression Avoidance

- Preserved SAGE artifact boundaries and exact gate marker formats.
- Kept S1 artifact-write-only behavior and did not allow product/source/config edits.
- Avoided making company skill files a runtime dependency when they may not be installed in every SAGE repo.
- Reserved implementation changes for later SAGE build agents rather than allowing review or interview agents to fix issues directly.

## Add SAGE Security Review Gate

### Rationale

SAGE needed a dedicated security review point between code review and final agent testing so security findings are not mixed into general code review or discovered only during S7. The security review flow was added as an explicit S6.5 step with its own artifact, standards reference, and hook gate.

The goal was to keep the security review mandatory only where the workflow config includes it, and to make it structurally consistent with the existing code review gate: the agent reports findings, writes a phase artifact, and downstream testing proceeds only when the exact gate marker shows zero Critical findings.

### Changes

- Added `security-reviewer` as an artifact-write-only S6.5 agent.
- Added `security-standards.md` as the security review rule source, grounded in Empyrean SDLC and OWASP secure coding practices.
- Added `security_review_gate.py` to block S7 until `phase-{N}-security-review.md` contains `Critical findings: 0`.
- Updated `code_review_gate.py` so S6.5 and S7 both require S6 code review to have zero Critical findings.
- Updated workflow config, hook registration, session manifest schema, hook script specification, cursor directory specification, and the agent catalogue to include the S6.5 security review artifact and gate.
- Updated `test-runner` so S7 respects the configured security-review prerequisite.

### Regression Avoidance

- Preserved the existing `Critical findings: N` marker pattern for gate compatibility.
- Kept the security reviewer report-only; it does not fix code or modify source/config files.
- Made the security gate mirror the existing code-review gate behavior rather than adding a separate review lifecycle.
- Avoided hardcoded Profitability object assumptions in security standards by requiring scoped contract verification for process, revision, Dataverse, and financial persistence checks.

## Align SAGE With ProfitabilityAPI.V2 Architecture and Tests

### Rationale

The first reconciliation pass improved SAGE's discovery and review depth, but the developer interview still implied the legacy API V1 DAL/service/controller stack as the default architecture. Profitability is migrating to `ProfitabilityAPI.V2` Clean Architecture, so SAGE agents need to distinguish V1, V2, frontend, and SQL-heavy scopes before asking questions or planning tests.

SAGE also needed clearer test-layer guidance from the Profitability `write-tests` skill so S2 planning, S5a RED test authoring, and S7 test execution map requirements to the correct layer instead of treating tests as one generic bucket.

### Changes

- Updated `dev-interview` feature exploration to classify scoped work as API V1, ProfitabilityAPI.V2, Angular, SQL-only, or mixed before tracing implementation paths.
- Added hybrid deferral to the Profitability `clean-arch-guide` skill when available, with a concise SAGE fallback summary for Domain, Application, Infrastructure, Presentation, Contracts, and Shared layer expectations.
- Added hybrid deferral to the Profitability `write-tests` skill when available, with concise fallback mapping for Domain unit tests, Application integration tests, E2E/API tests, contract serialization tests, architecture guards, frontend Vitest tests, and Playwright tests.
- Updated `implementation-planner`, `test-author`, and `test-runner` to use the skill-first/fallback pattern instead of duplicating the full product skill content.

### Regression Avoidance

- Kept the V1 exploration path for legacy scoped files.
- Did not make the Profitability repo skills a hard runtime dependency; SAGE defers to them by name/path when available and uses concise fallback rules when they are absent.
- Preserved the S5 split: `test-author` writes tests only, `tdd-builder` remains responsible for production code.
- Kept Playwright conditional on `featureFlags.playwrightE2E`.
