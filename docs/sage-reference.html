Team Introduction · v1.0 · 2026

The SAGE Framework

A repeatable, enforced path from feature idea to production-ready code — using AI as the primary executor, with human judgment at every critical gate.

Profitability Team Status: Approved ~6–7 days to live
1

What is SAGE?

SAGE = Semi-Autonomous Guided Execution. It is a structured workflow framework that rebuilds mob programming principles for distributed teams — with AI as the primary code executor and humans as the decision-makers at critical gates.

The core problem SAGE solves: as teams adopt AI-assisted development, output quality becomes inconsistent. One developer gets great results; another gets hallucinated code. One session produces verified, tested features; another produces something that breaks in review.

SAGE makes quality an enforced structural property of the process, not a function of individual skill or prompting technique. Because the gates are implemented in code — not in instructions — an AI agent cannot skip them.

Three things SAGE replaces

Story point estimation

Replaced by SAGE Intel — empirical velocity data from every completed phase. Planning uses real delivery history, not guesses.

Manual ADO work tracking

Replaced by Linear with structured states, auto-linked commits/PRs, and machine-readable metadata blocks.

"It worked on my machine" reviews

Replaced by 12 enforced hook gates — tests must pass, code review must clear Critical findings, completion reports must exist.

2

The Four Layers

SAGE operates across four interconnected layers. Each layer has a distinct purpose and can evolve independently.

⚡
Layer 1
Execution Structure

Four workflow modes matched to team configuration and feature type. Eight build steps (S1–S8) within each phase provide a consistent, verifiable delivery path.

🔒
Layer 2
Enforcement

Twelve Python hook scripts integrated into Cursor's execution layer. Every step transition is gated. Agents cannot skip steps or declare work complete without verifiable artifacts.

🧬
Layer 3
SAGE Hone

The self-improving subsystem. Every session is observed via telemetry. Every 5 cycles, AI performance is evaluated and evidence-backed improvements are proposed. Changes require human approval.

📊
Layer 4
SAGE Intel

Delivery intelligence from every completed cycle. Powers the intel-advisor for weekly planning and release forecasting. No human estimation required.

S1–S8 Build Steps

Every phase runs the same eight build steps. The session manifest tracks which step is current. Gates fire at each transition — you cannot proceed without completing the prior step.

S1
Dev Interview

The dev-interview agent conducts a structured interview. Plan-only mode — no code writes permitted.

Plan mode enforced
S2
Implementation Plan

The implementation-planner produces a machine-readable plan artifact from the S1 interview output.

Gate: S1 artifact required
S3
Traceability Review

The traceability-reviewer checks the plan against the PRD. Blocker count must reach zero before proceeding.

Gate: Zero blockers required
S4
Validation Mockup

The validation-generator produces an HTML mockup or calculation proof. A human must set validationConfirmed: true — an agent cannot set this flag.

Human confirmation required
S5
Build / TDD

Primary build step with TDD. The code-simplifier runs post-RGR. In Sprint mode, dependent phases wait for foundation merge.

Gate: Required refs + validation confirmed
S6
Code Review

The code-reviewer reviews against the implementation plan. Zero Critical findings required to proceed.

Gate: No Critical findings
S7
Agent Testing

The test-runner executes the test suite. The gap-analyzer checks coverage gaps via Playwright MCP. Test results must contain STATUS: PASS.

Gate: STATUS: PASS required
S8
Completion Report

The feature-doc-generator produces the completion report. The stop gate requires passing test evidence from S7 before the agent can end its turn.

Gate: Pass evidence required to stop → Telemetry recorded
3b

Build Modes: Autonomous vs Checkpoint

At S1, the developer sets the build mode. Both run the same S1–S8 gates — the difference is pacing and visibility during S5.

AUTONOMOUS
Full-run mode

The agent executes the entire S5 build cycle without pausing between tasks, running tests after each task and self-correcting on failures.

⚡
Speed: Fastest — no interruptions between tasks.
👁️
Visibility: Developer reviews full output at S6 (code review).
🔒
Gates still enforced: All 12 hook gates fire regardless of mode.
Use when: phase is well-understood, implementation plan is detailed.
CHECKPOINT
Batch-confirm mode

TDD tasks split into confirmation batches. Agent builds one batch, pauses, and waits for the developer to review and confirm before proceeding.

🛑
Pause points: Agent stops after each batch and waits for the developer to set the confirmation flag.
🧭
Course-correction: Easier to catch a wrong direction early, before subsequent batches run.
🔒
Gates still enforced: batch_confirmation_gate hook rejects the next batch without the human-set flag.
Use when: phase is exploratory or involves complex logic.
How to set it: At S1, the developer records the mode in the session manifest under buildMode. The orchestrator reads this at kick-off and configures batch confirmation blocks accordingly.

Workflow Modes

Choose a mode based on team availability, feature complexity, and how much real-time collaboration adds value. All modes run the same S1–S8 steps.

MOB
Mob
Single terminal, sequential phases. Full team on screen share. Driver + Navigator roles. Mob Kick-off (~2 hrs) required.
Best for: onboarding, collaborative features, complex decisions
SPRINT
Sprint
Parallel git worktrees, each developer owns one phase. Sprint Kick-off (~75 min). Phases run simultaneously, then merge in dependency order.
Best for: multi-component features needing parallel execution
PAIR
Pair
Two developers, sequential phases, no synchronous kick-off. PRD required at Ready status. Async phase breakdown only.
Best for: medium complexity with knowledge transfer value
SOLO
Solo
Single developer, no kick-off. No PRD required — a Linear issue is sufficient. All 12 hook gates still active.
Best for: hotfixes, minor enhancements, contained work
Phased adoption: Sprint and Solo modes launch first. Mob and Pair are introduced once Sprint is running stably.

Operating Principles

These five principles govern how SAGE is designed and how it should be operated.

01
Structural enforcement over agent instruction

Quality gates are hook scripts that reject tool calls at the execution layer. An AI agent cannot skip a step regardless of what it is instructed to do.

02
Artifact quality determines pipeline quality

A feature cannot enter the build phase without a PRD scoring 80/100 or above. The component specification is a required artifact, not a best-effort addition.

03
Async-first, synchronous by exception

Synchronous sessions are reserved for decisions that benefit from real-time discussion. Everything else flows asynchronously.

04
Evidence over estimation

No human estimation is used at any stage. All effort estimates and release forecasts are derived from the SAGE Intel empirical dataset.

05
Self-improvement is automatic, approval is human

SAGE Hone proposes improvements to AI instructions based on evidence. Every proposed change is staged for human review before being applied.

What is SAGE Intel?

SAGE Intel is the data layer of the framework. It replaces human estimation with measured delivery history. Every time a phase completes, metrics are automatically recorded. After enough cycles, the recorded data becomes the source of truth for all planning and forecasting.

There is no manual input at any stage. The PM asks @intel-advisor questions; the advisor reads the dataset and responds with confidence-qualified estimates. The Lead Dev reads session performance reports to track agent quality trends over time.

SAGE Intel encompasses two related subsystems — Intel (data capture + advisory) and Hone (quality evaluation + self-improvement) — because both feed the same reporting surface and are read by the same people.

Three things SAGE Intel replaces

Story point estimation
Velocity baselines
Empirical median actual hours per layer, per mode. Improves automatically as cycles complete.
Sprint planning guesswork
Capacity advisory
intel-advisor reads the dataset and produces confidence-qualified estimates with explicit sample counts.
Post-mortem reviews
Cycle performance reports
session-performance-evaluator scores every cycle across 5 dimensions and surfaces systematic violations automatically.
2

The Two Subsystems

SAGE Intel and SAGE Hone are distinct subsystems but are documented together because they share the same consumers (PM and Lead Dev), the same reporting surface (Notion and Linear), and are both triggered at the same moment — after cycle close.

Session Performance Evaluator

Scores every completed work cycle across five dimensions. Identifies systematic violations — agents attempting to bypass gates, repeated hook rejections of the same type — and creates Linear issues for the Lead Dev when violations are detected.

How to invoke

Cursor — Agent chat · Lead Dev · after cycle close
@session-performance-evaluator Evaluate cycle [session-id]

The 5 scoring dimensions

A
Step Compliance
All S1–S8 executed in correct sequence with all artifacts present
›
OK

All steps S1–S8 in correct sequence. All required artifacts present. Solo mode exception: S1 (dev interview) is not required.

Warning

One artifact missing or one step with anomalous duration (>2× estimate). No steps skipped.

Fail

Any step skipped. Any two steps combined. Step sequence does not match manifest progression.

B
Hook Discipline
Hook rejections per step — one-off vs repeated
›
OK

0–1 rejections per step. A single rejection is healthy — the hook worked correctly.

Warning

2–3 rejections of different types. Agent is probing, not repeating the same mistake.

Fail

3+ rejections of the same type on the same step. Also: any file write attempt in Plan mode beyond the first, or any stop hook rejection at S8.

C
TDD Cycle Quality
GREEN first-pass rate and REFACTOR completion rate
›
OK

GREEN first-pass rate ≥70%. REFACTOR completion rate ≥80%. RED discipline maintained: test written before implementation.

Warning

GREEN first-pass 50–69%, or REFACTOR completion 60–79%. Indicates the implementation plan may need better task granularity.

Fail

GREEN first-pass <50% — implementation plan was poorly formed. REFACTOR completion <60%, or GREEN attempted before RED confirmed failing.

D
Gate Bypass Attempts
Agent attempts to set human-only flags in the manifest
›
OK

No bypass attempts detected. The agent did not try to set validationConfirmed or batches[N].confirmed via a tool call.

Warning

No intermediate warning state — this dimension is binary.

Fail — automatic

Any detected bypass attempt. This is always an automatic Fail and always creates a Linear violation issue, regardless of all other dimension scores.

E
Phase Duration
Actual vs estimated hours from the manifest
›
OK

Actual duration within 25% of the estimate in the session manifest.

Warning

25–50% over estimate. This contributes to calibration data even when flagged — the intel-recorder still records the actual duration.

Fail

More than 50% over estimate, or phase abandoned without completing S8.

Systematic violations always create a Linear issue. A violation is systematic when: the same hook rejection type fires 3+ times on the same step in one phase, Dimension D fails (any bypass attempt), or the same Fail pattern appears across two consecutive cycles. All systematic violations are assigned to the Lead Dev in Linear automatically.
